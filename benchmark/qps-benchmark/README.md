# QPS 对比：平台线程池 vs Kotlin 协程桥接

这个基准回答一个问题：**在等待模型响应的场景里，协程桥接到底值不值得？**

它模拟一次固定延迟的 LLM 调用，比较三种执行方式：

| 变体 | 说明 |
| --- | --- |
| `platform-pool-8` | 8 个平台线程 + 阻塞 `gateway.one()` |
| `platform-pool-1000` | 1000 个平台线程 + 阻塞调用，用线程数换并发 |
| `coroutines-8` | 8 个协程载体线程 + `LlmCoroutines.one()`，等待发生在挂起点 |
| `java-async` | 纯 Java `gateway.oneAsync()` + `CompletableFuture`，不使用协程 |

模拟延迟由独立调度器完成，等待期间不占业务侧线程——这和真实 LLM 调用的主要形态一致。

## 运行

先安装本仓库的 SNAPSHOT：

```bash
mvn -B install -DskipTests
```

再运行基准：

```bash
cd benchmark/qps-benchmark
mvn -B compile exec:java -Dexec.args="3000 50 8"
```

参数依次是：总调用数、单次模拟延迟（毫秒）、协程载体线程数。

## 实测结果

环境：Windows 10、JDK 8u292、8 核；`calls=3000`、`latency=50ms`、`carriers=8`。

| 变体 | 墙钟(ms) | QPS | 峰值线程数 |
| --- | ---: | ---: | ---: |
| `platform-pool-8` | 23313.1 | 128.7 | 28 |
| `platform-pool-1000` | 195.2 | 15372.7 | 1017 |
| `coroutines-8` | 87.6 | 34257.3 | 26 |
| `java-async` | 72.1 | 41594.0 | 18 |

解读：

- 8 线程阻塞池的吞吐被“线程数 / 延迟”锁死：`8 / 0.05s ≈ 160 QPS`，实测 128.7。
- 1000 线程池把 QPS 拉到 1.5 万，代价是 1000 个平台线程；3000 个调用还要分三波。
- 8 个协程载体达到 3.4 万 QPS，线程数和 8 线程池同一量级。所有调用同时在途，不受“波次”限制。
- 纯 Java 异步 API 也达到 4.2 万 QPS、18 个线程，说明**吞吐提升主要来自异步 I/O**，协程解决的是“保持顺序写法 + 取消传播”，不是把 I/O 变快。
- 协程和 Java 异步之间谁高谁低是运行间波动（多次复跑约 3.3–3.7 万 vs 3.4–4.2 万），不要把这 20% 当作协程的性能优势。

## 方法说明

- 每个变体开始前调用 `ThreadMXBean.resetPeakThreadCount()`，并等待上一个变体的线程退出，避免线程峰值串味。
- 平台线程池使用 `prestartAllCoreThreads()`，测的是稳态吞吐，不把线程创建时间算进 QPS。
- 阻塞变体的 p50 是任务开始后的服务时间，不含排队；排队成本体现在墙钟和 QPS 上。
- 协程变体的“服务端”是一个单线程调度器，故意不让它成为并发来源。

## 这个基准不证明什么

- 不证明协程比线程“计算更快”。这里没有 CPU 密集任务，只有等待。
- 不证明协程是拿到高 QPS 的唯一方式：`java-async` 说明纯 `CompletableFuture` 也行。
- 不代表真实网络环境。真实链路里还有 OkHttp dispatcher、连接池、服务端并发和带宽限制。
- 数字和机器强相关。8 核机器上 1000 个平台线程已经很重；核数更少时差距会更明显。

结论：**在 JDK 8 的 I/O 等待型负载里，异步 I/O 是吞吐的主要来源；协程桥接让 Kotlin 代码保持顺序写法，同时用个位数载体线程达到千线程池的吞吐；需要真虚拟线程时，JDK 21 模块可以无缝替换。**
