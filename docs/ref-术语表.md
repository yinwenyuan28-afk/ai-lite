# 术语表

本文把各文档里反复出现的术语翻成**人话**。按层分组；每个词先给一句大白话，必要时补一句准确定义。各篇文档首次用到这些词时应该就地解释，忘了再回这里查。

定位：所有文档共用的字典，不讲故事。故事看 [架构总览](desc-架构总览.md)，一次调用的完整旅程看 [单次模型调用入口](desc-单次调用.md)。

---

## 1. 通用

| 术语 | 人话 |
| --- | --- |
| 竞态（race） | 两件事几乎同时发生，谁先谁后不确定，结果取决于运气 |
| 幂等 | 同一件事做多次和做一次，效果一样 |
| 不变量 | 无论怎么执行都必须保持成立的规则，比如「许可总数 = 配置的并发数」 |
| best-effort | 尽力做到，但不打包票（对应的是「保证」） |
| O(1) | 固定几步操作就完事，工作量不随数据量增长 |
| 回灌 | 本不该参与计算的样本又被算进去。本文档里通常指：被拒绝的调用不该被当成失败样本喂给熔断窗口 |
| 语义 | 一段行为对外承诺的准确含义，比如「取消语义」= 取消后到底发生什么、不发生什么 |
| 收敛 | 几条岔路最终都到达同一个确定的终点，不会悬在半空 |
| 终态 | 不会再变的最终结果（成功、失败、取消三者之一），定了就不再改写 |

## 2. HTTP 传输层

| 术语 | 人话 |
| --- | --- |
| 传输（`LlmTransport`） | 负责「把请求发给供应商、把响应拿回来」的组件，按协议（OpenAI/Anthropic 等）各有一个实现 |
| HTTP 执行器（`HttpExecutor`） | 传输底下真正干网络 I/O 的组件；传输管「怎么拼报文」，执行器管「怎么发出去」 |
| 传输线程 | HTTP 客户端自带的线程（如 OkHttp Dispatcher 的线程），真正的 socket 收发都在它上面。它是所有调用共享的，所以上面的代码必须快进快出 |
| 非阻塞提交 | 把请求「递」给 HTTP 客户端就返回，不等响应；响应到了由回调通知 |
| 回调（callback） | 「事情完成了请打这个电话」——你留给 HTTP 客户端的函数，完成时由它的线程来调 |
| SSE | 服务器往一条连接里持续推数据的格式，模型的流式输出走的就是它 |
| NIO | 不用一个线程死等一个连接，少量线程看管大量连接的 I/O 方式 |
| 非合作传输 | 取消时不会立刻停下来响应的传输实现（如 JDK 8 的正文读取阶段），框架对它有兜底路径 |

## 3. 网关层（LlmGateway）

| 术语 | 人话 |
| --- | --- |
| 名额（permit） | 并发上限的通行证。一次尝试领一张，响应回来就还；只在配了 `guard.concurrency` 时存在 |
| 闸门 | 发放名额的那道关卡。同步等待者和异步排队者排同一个队 |
| 出口保护 | 并发上限、熔断、多 key 轮换三件事的统称，纯配置、默认全关 |
| 熔断 | 供应商连续失败太多就「拉闸」：一段时间内直接拒绝、一个请求都不发，免得把坏情况拖得更糟 |
| 拉闸 / 熔断打开（OPEN） | 熔断器拒绝一切请求的状态 |
| 试探（HALF_OPEN） | 熔断冷却结束后只放行一个请求去「探路」：成功就恢复正常，失败就继续拉闸 |
| 采样 / 记账 | 每次调用的结局（成功/失败）被记进熔断的统计窗口，供「要不要拉闸」判断用 |
| 窗口 | 统计失败率的最近一段时间范围 |
| 冷却 | 一个 key（或熔断器）犯错后被罚「禁闭」一段时间，期间不用它；时间到了自动恢复 |
| 游标 | 多 key 轮换里「当前指向哪把 key」的指针 |
| 轮换 | 多把 api key 之间换着用。本项目只在失败时换（挨罚的冷却，下次取下一把），不是均匀轮流 |
| 退避（backoff） | 重试前先等一会儿再试，避免火上浇油；本项目默认指数增长（200ms → 400ms → 800ms…） |
| 抖动（jitter） | 退避时间乘一个 0.8~1.2 的随机系数，防止大量调用者同时醒来扎堆重试 |
| Retry-After | 供应商在 429/503 响应里告诉你的「过 N 秒再来」，重试等待会优先听它的 |
| 零出站 | 一个 HTTP 请求都没发出去（比如被校验、熔断、名额拒之门外时） |
| 分段睡眠 | 同步重试的等待方式：每次只睡 50ms 就醒来看看有没有取消，取消了立刻走 |
| 尝试 / attempt | 一次真实的模型请求。重试 = 多次尝试；每次尝试独立领名额、独立写调用记录 |

## 4. 协程与线程

| 术语 | 人话 |
| --- | --- |
| 挂起（suspend） | 协程「暂停等结果」，期间把线程让给别人用；跟「阻塞」（线程傻等不动）是两回事 |
| 恢复 | 结果好了，协程从暂停的地方接着跑 |
| 协程 | 一种用户态的「轻量任务」：可以在等 I/O 时主动让出线程，等到了再回来，成千上万个协程共用少量线程 |
| 载体线程 | 协程运行时所在的平台线程。协程挂起时它去跑别的协程，恢复时再回来。数量少、很宝贵，所以阻塞操作别放上去 |
| 续体（continuation） | 协程「接下来怎么跑」的打包记录。挂起时存起来，恢复时拿着它继续 |
| CPS | Continuation-Passing Style，把「后面要做的事」当参数传给被调函数的写法。Kotlin 编译器把 suspend 函数自动改写成这种形式 |
| 蹦床（trampoline） | 用「循环代替递归」的结构：每步算完把下一步登记到队列，循环从队列取，避免递归把栈压爆 |
| 泵（pump） | 一个不停取事件、推进状态的循环。AgentLoop 异步版的推进就集中在一个泵循环里 |
| dispatcher() | 协程库拿来「把协程派到哪条线程跑」的调度器，本项目里就是载体池 |
| io() | 同一个载体池的普通 Executor 视图。注意：往里放阻塞任务会把载体线程占住 |
| 虚拟线程（JDK 21+） | JDK 自带的「轻量线程」：阻塞时自动让出底层线程，写法跟普通线程一样但成本极低 |
| pinning | 虚拟线程卡在 `synchronized` 块里没法让出底层线程的现象（JDK 21–23 存在，24 起大幅缓解） |
| park | 线程「睡觉」等信号（JDK 的 `LockSupport`），睡着时不占 CPU |
| 结构化并发 | 协程的生命周期跟着作用域走：作用域取消，里面所有协程一起取消，不会漏 |
| `ai-lite-retry-*` | 框架的定时调度线程，只干「退避时间到，发起下一次尝试」这一件事 |
| `ai-lite-*`（载体池） | 框架自备的后台线程池，承接排队转接、调用记录落盘等杂活（线程名前缀可配，默认 `ai-lite-`） |

## 5. 编排层（AgentLoop / Workflow）

| 术语 | 人话 |
| --- | --- |
| 编排层 | 比「单次调用」高一层的东西：自动管理工具循环、多步骤流程（AgentLoop、Workflow、会话循环） |
| 工具循环 | 模型说「我要用工具 X」→ 框架执行 → 把结果发回模型 → 直到模型给出最终回答 |
| 一轮 / round | 工具循环里「模型说一次话」算一轮 |
| 钩子（hooks） | 框架在固定时机回调你的函数（轮前、轮后、出错等） |
| `decideRound` | 每轮结束后「接下来干什么」的统一决策点（继续、取消、到上限），同步异步共用一份 |
| afterRun | 一次运行收尾时必做的清理/记录步骤，无论成败都要执行 |
| stopReason | 模型或框架给出的「为什么停」标记（正常结束 STOP、被打断 ABORTED、轮数用尽 MAX_ROUNDS 等） |
| 终态优先级 | 多个结局同时竞争时听谁的：取消 > 钩子叫停 > 轮数用尽 > 模型自身标记 |
| 步骤（Step） | Workflow 的执行单元：SyncStep（同步函数）或 AsyncStep（返回 future） |
| 背压（backpressure） | 下游消费不过来时，把压力反馈给上游让它慢下来（如流式回调队列塞满 → 以 OVERLOAD 结束） |
| per-call 串行执行器 | 每个调用专属的小队列：回调按顺序执行，一个调用慢不拖累别的调用 |
