# JDK 8 + Jetty 传输下的栈与内存风险（静态分析 + 实测）

> **这份报告回答两个问题**：一是代码逻辑上有没有能把栈打爆、把堆撑爆的地方；二是用本机假模型服务按 A104527 的真实调用形态压过之后，实际会不会发生。
> 
> **一句话结论**：**没有发现慢性内存泄漏**（连续压测后 GC 完的留存都是 0）；但发现了**一处真实的峰值膨胀**——单个 4MB 的流式响应会让堆峰值多出约 76MB，放大 19 倍，原因是 `OpenAiCompletionsTransport` 无条件把整个响应体复制在内存里，且没有任何上限。另外 Jackson 2.9 没有嵌套深度上限，5000 层嵌套就会 `StackOverflowError`。
> 
> **配套工具**：`benchmark/fake-llm-server/`（本次新建，不参与 reactor 构建）。

## 1. 测试环境与方法

### 1.1 环境

| 项       | 值                                                             |
| ------- | ------------------------------------------------------------- |
| JDK     | OpenJDK 1.8.0_292                                             |
| Jackson | 2.9.10.1（由 Spring Boot 2.1 管理，**没有** `StreamReadConstraints`） |
| Jetty   | 9.4.22.v20191022                                              |
| 传输      | `JettyHttpExecutor`（NIO selector 驱动）                          |
| 默认最大堆   | 3481 MB                                                       |

### 1.2 方法

用 `MemoryProbeMain` 驱动**真实的** `LlmGateway` + `JettyHttpExecutor`，打本机 `FakeLlmMain`。这样复现的是生产的调用链路，不是模拟的。

每个场景的做法：

1. 先做 3 次 GC 取基线（看「存活集」而不是「刚分配量」）
2. 并发压 N 次调用
3. 再 3 次 GC 取终值，算留存增量
4. 全程 20ms 采样堆峰值（GC 完的留存看不出「同一时刻占了多少」，而峰值恰恰是大响应体的问题所在）

**关键设计**：每个场景**连跑两遍**。第一遍让 Jetty 把一次性线程/连接池扩到位，第二遍才是稳态。两遍对比就能区分「一次性扩容」和「每调用漏一个」——后者两遍增量会一样大。

## 2. R-01：流式响应体被完整复制且无上限（高 · 已修复）

### 2.1 问题所在

`ai-lite-llm/src/main/java/.../transport/OpenAiCompletionsTransport.java:91`

```java
final State state = new State();
final StringBuilder raw = new StringBuilder();          // ← L91，这里
final TransportSupport.SseCollector sse = new TransportSupport.SseCollector();
return async.executeStreamingAsync(httpRequest, new StreamListener() {
    @Override
    public void onLine(String line) {
        raw.append(line).append('\n');                  // ← L96，无条件累积每一行
        String payload = sse.accept(line);
        if (payload != null) {
            handleEvent(payload, state, request);
        }
    }
})
```

`raw` 只在一种情况下被用到（`:113`）：

```java
if (!state.sawData && raw.length() > 0) {
    return parseBlocking(raw.toString());   // 兼容：响应不是 SSE、而是整段 JSON
}
```

也就是说：**正常流式响应下 `raw` 完全没用，但内存照涨**。而且这个累积**没有总量上限**——`Utf8LineBuffer` 限制的是「单行 1MB」，不是「整个流」。

同一份数据在堆里同时存在多份：

- `Utf8LineBuffer` 读进来的字节数组
- 解码出的 `String line`
- `raw` 里的一份副本
- `State.content` 里又一份
- 最后 `parseBlocking(raw.toString())` 再来一次 `toString()` 拷贝

### 2.2 实测数据

`--concurrency=1`（排除并发叠加，单看一个请求的放大倍数）：

| 场景          | 响应体  | 并发  | 堆峰值          | 放大倍数 |
| ----------- | ----:| ---:| ------------:| ----:|
| 大分片 16×64KB | 1 MB | 1   | +37.8 MB     | ~38× |
| 单个 4MB 流式   | 4 MB | 1   | **+75.7 MB** | ~19× |

`--concurrency=8`：

| 场景          | 响应体  | 并发  | 堆峰值         |
| ----------- | ----:| ---:| -----------:|
| 大分片 16×64KB | 1 MB | 8   | **+610 MB** |
| 单个 4MB 流式   | 4 MB | 8   | **+529 MB** |

### 2.3 这是不是真问题，取决于响应有多大

这一条**不能脱离你们的实际响应体大小来判断**：

- A104527 生产配置是 `context-window: 131072`、`max-tokens: 8192`。
- 如果模型真的只返回 8192 token（中文约 25KB 字符），那么 25KB × 19 ≈ 475KB，可以忽略。
- 但 `LlmBenchProfiles` 里有 75 秒的 `long-review` 和 90 秒的 `deep-analysis`。如果这两档真会返回大文本，叠加并发后就是上面的 610MB 量级。

**这个量级问题在修复后已不再是阻塞项**：惰性累积让正常流式路径不再产生额外副本，无论响应多大都只留一份正文。剩下的上限问题见 R-04（`State.content` 无上限）。

### 2.4 修复方向

> **已实施（2026-11-09）**：采用下面的方案 2「惰性累积」，见 §2.5。

三个层次，从保守到彻底：

1. **加总量上限**：给 `raw` 设一个上限（比如 4MB 或与 `max-tokens` 换算），超过就停止累积并标记，只在 `!sawData` 那条兼容路径上才需要它。
2. **惰性累积**：默认不累积，只有判定为「假流式」之后才开始保留。
3. **只在需要时保留原始字节**：把兼容逻辑改成「先探测首字节」，不需要的路径根本不进累积器。

注意：改 R-01 会碰到 `!state.sawData` 那条兼容回退路径（有些供应商声称流式、实际返回整段 JSON）。**改动必须先补一条覆盖该回退路径的测试**，否则会把兼容性改坏。

### 2.5 已实施：惰性累积（2026-11-09）

#### 做法

把 `StringBuilder raw` 换成一个专门的 `RawFallback` 内部类，同步与异步两条流式路径共用。核心是把判定从「流结束」挪到「第一个有内容的行」：

```java
void accept(String line) {
    if (line == null) {
        return;
    }
    if (sse == null) {                       // 还没判定
        if (line.trim().isEmpty()) {
            return;                          // 空行不参与判定
        }
        sse = Boolean.valueOf(isSseLine(line));
        if (sse.booleanValue()) {
            return;                          // 真流式：永不累积
        }
    }
    if (sse.booleanValue()) {
        return;
    }
    text.append(line).append('\n');          // 只有假流式才累积
}
```

`sse` 的取值：`data:` / `event:` / `id:` / `retry:` / `:`（注释行）这几种前缀都认作 SSE 语法。

**为什么跳过空行**：SSE 允许事件之间有空行，真实响应也可能以空行开头。如果不跳过，一条以空行开头的正常 SSE 会被误判成假流式，然后把 `data: {...}` 文本交给 `parseBlocking`，解析失败。

#### 先锁行为再改代码

改之前发现这条兼容路径**完全没有测试覆盖**。新增 `OpenAiCompletionsStreamFallbackTest`（9 条用例），先确认全部为绿，再改产品代码，改完再跑仍全绿。

| 测试 | 保护什么 |
| --- | --- |
| `claimedStreamButReturnedPlainJsonStillParses` | 假流式仍能解析出内容、stop、usage |
| `plainJsonFallbackKeepsReasoningSeparate` | 假流式下 reasoning 与 content 分开 |
| `plainJsonFallbackKeepsToolCalls` | 假流式下工具调用能解析 |
| `realSseConcatenatesAllDeltas` | 真流式多事件拼接 |
| `realSseIsNotTreatedAsPlainJson` | 真流式不被误判成假流式（判定写错时首先红的就是它） |
| `largeSseAccumulatesEveryEvent` | 200 条事件逐条累积、不缺不重 |
| `leadingBlankLineDoesNotBreakSseDetection` | 首行为空行时判定仍正确 |
| `sseCommentLineIsIgnored` | 注释行被忽略而非当成数据 |
| `emptyStreamYieldsEmptyCompletion` | 空流返回空内容而不是异常 |

#### 效果实测

`HeapCeilingProbeMain`：4MB 流式响应，逐步压小堆看能否成功。

| 堆上限 | 改前 | 改后 |
| --- | --- | --- |
| 32 MB | — | 失败 |
| 36 MB | — | **失败**（`LlmCallException: 模型调用失败`） |
| 43 MB | **失败** | **成功** |
| 48 MB（→43MB 实际） | 失败 | **成功** |
| 58 MB | 成功 | 成功 |
| 64 MB（→57MB 实际） | 成功 | 成功 |

**最小堆需求从 43–58MB 降到 32–43MB，省约 15MB**（4MB 响应体的近 4 倍）。

同时「结束后堆占用」从 43MB 降到 36MB（64MB 那组）、从 27MB 降到更低位，说明常态占用也下降了。

#### 没有做的事

- 没动 R-04（`State.content` / `State.reasoning` 无上限）——那是「需要的数据没有边界」，和这次「不需要的数据也留着」是两回事。
- 没动同步路径 `streaming()` 之外的其他协议适配器——`OpenAiResponsesTransport` 和 `AnthropicMessagesTransport` 本来就没有这个累积器。

## 3. R-02：Jackson 无嵌套深度上限（中）

### 3.1 实测

`StackDepthProbeMain` 直接调用 transport 实际使用的 `AiLiteJson.readTree`：

```
Jackson: 2.9.10.1
  深度    999 -> parsed
  深度   2000 -> parsed
  深度   5000 -> StackOverflowError   ← 第一个失败点
  深度  20000 -> StackOverflowError
  深度 100000 -> StackOverflowError
```

`StreamReadConstraints`（默认 max nesting depth 1000）是 **Jackson 2.15** 才引入的。Spring Boot 2.1 管理的是 2.9.10.1，**没有这个保护**。

### 3.2 现有的错误处理挡不住它

`TransportSupport.parse()` 只捕获 `RuntimeException`：

```java
} catch (LlmCallException ex) {
    throw ex;
} catch (RuntimeException ex) {          // ← StackOverflowError 是 Error，不在这里
    throw new LlmCallException("模型响应无法解析", ex, LlmCallException.Kind.PARSE);
}
```

`parseBlocking` 同样只捕获 `LlmCallException` 和 `RuntimeException`。`StackOverflowError` 全部穿透。

### 3.3 实测中它为什么没造成灾难

我用 20000 层嵌套压了 200 轮（并发 16）：

- 全部 200 次失败，错误是 `LlmCallException("模型调用失败")`
- **没有一次挂死**（无「60 秒内只收敛 N 个」告警）
- 线程数不涨，堆不涨

原因是 `thenApply(result -> parseBlocking(...))` 的异常被 `whenComplete`/`handle` 兜住，转成了 future 的异常完成。

流式路径上也有一层 `catch (Throwable)` 兜底——`JettyHttpExecutor.java:289`：

```java
try {
    for (String line : lines.accept(bytes)) {
        listener.onLine(line);          // ← 流式回调在这里
    }
} catch (Throwable ex) {                // ← Error 也会被接住
    failed.set(true);
    future.completeExceptionally(streamFailure(ex, request.getCancel()));
    jettyRequest.abort(ex);
}
```

所以**两条路径都不会让 `StackOverflowError` 逃到 Jetty 线程池上**。这一条经过代码复核确认，不是运气好。

但流式实测 20000 层仍报「成功」，原因是 R-03：`handleEvent` 里的 `catch (LlmCallException)` 在更内层就把解析失败吞掉了，根本轮不到 `JettyHttpExecutor` 的 `catch (Throwable)`。两层兜底之间存在一层「静默丢弃」，把错误消化成了空内容。

### 3.4 修复方向（未实施）

在 `TransportSupport.parse()` 和 `parseBlocking()` 里把 `Error` 也纳入捕获范围，只捕获 `StackOverflowError`（不要捕获所有 `Error`，避免吞掉 `OutOfMemoryError`）：

```java
} catch (StackOverflowError error) {
    throw new LlmCallException("模型响应嵌套过深", error, LlmCallException.Kind.PARSE);
}
```

或者在解析前先做一次快速的括号深度扫描，超限直接拒绝。后者更省资源，但多一遍遍历。

## 4. R-03：流式解析失败被静默吞掉（中）

`OpenAiCompletionsTransport.handleEvent()`：

```java
JsonNode root;
try {
    root = TransportSupport.parse(payload);
} catch (LlmCallException ex) {
    return;                       // ← 静默丢弃这个事件
}
```

**后果**：一个格式错误的事件被丢弃，流继续，最后返回的是一份**内容残缺但"成功"**的结果。实测 20000 层深嵌套的流式场景报「成功 200 次」，而同一负载的非流式场景报「失败 200 次」——两条路径对同一份坏数据给出了完全不同的判定。

**为什么这比 R-02 更值得注意**：栈不会爆、内存不会涨，但**数据会静默变少**。如果模型返回的某个 SSE 事件因为编码问题解析失败，用户拿到的是一段缺字的内容，而不是一个错误。

**修复方向**：解析失败时不应静默 `return`。至少应该记录失败次数，超过阈值就终止整个流并报 `PARSE` 错误。需要注意的是，有些供应商会在流里发送非标准事件（比如注释行、心跳），这类应当允许跳过——所以要区分「空/非 data 行」和「data 行但解析失败」。

## 5. R-04：累积全文无上限（中）

`State`（`:474`）里：

```java
private final StringBuilder reasoning = new StringBuilder();
private final StringBuilder content = new StringBuilder();
```

`handleEvent` 每次都 `state.content.append(content)`（`:411`）、`state.reasoning.append(reasoning)`（`:403`），**没有任何上限**。

这一条和 R-01 的区别：R-01 是「不需要的数据也留着」，R-04 是「需要的数据没有边界」。后者理论上合理（就是要拿全文），但如果上游返回一个 500MB 的响应，`content` 会吃到 OOM 为止。

**实际影响**：有 `max-tokens` 约束时问题不大——那是供应商侧的生成上限。但如果供应商不遵守（或者被中间人改包），就没有任何本地防线。

**修复方向**：给 `content` / `reasoning` 设上限，超限抛 `PARSE` 或 `TRANSPORT` 错误。数值建议从 `max-tokens` 换算，或用一个宽松的绝对上限（如 32MB）。

## 6. R-05：`SseCollector` 单事件累积无上限（中高）

`TransportSupport.java:118-153`：

```java
static final class SseCollector {

    private final StringBuilder data = new StringBuilder();   // ← 无上限

    String accept(String line) {
        if (line.trim().isEmpty()) {
            return flush();          // 只有空行才清空
        }
        if (line.startsWith("data:")) {
            ...
            data.append(chunk);      // ← 一直追加
        }
        return null;
    }
```

SSE 规范里一个事件由**空行**结束。`Utf8LineBuffer` 限制的是「单行 1MB」，管不到「多少行拼成一个事件」。如果服务端持续发 `data:` 行却永不发空行，`data` 会一路涨到堆耗尽，而且 OOM 落在 Jetty 回调线程上。

三个协议适配器全部经过它：`OpenAiCompletionsTransport:99`、`AnthropicMessagesTransport:76`、`OpenAiResponsesTransport:74`。所以这不是单协议问题。

### 6.1 实测

假服务新增 `bench-never-end=true` 模式（只发 `data:` 行、不发空行）。单次调用、2000 行、每行 1KB（约 2MB 数据）：

| 场景           | 响应数据量         | 并发  | 堆峰值          |
| ------------ | -------------:| ---:| ------------:|
| SSE 事件永不结束   | ~2 MB（2000 行） | 1   | **+46.4 MB** |
| 对照：正常 20 条分片 | 20 B          | 1   | +3.5 MB      |

累积是**单调的**，取决于服务端愿意发多少行——没有本地上限。`-Xmx256m` 下持续发送即可 OOM。

### 6.2 触发条件

- 恶意或错误的服务端
- 某些网关在长连接里复用事件、忘记发空行
- 代理层把 `\n\n` 改写掉

**这一条是子代理静态分析发现、我实测确认的**，压测默认场景测不到（假服务正常模式下每帧都以空行结束）。

### 6.3 修复方向

给 `data` 设上限（比如 1MB，与 `MAX_LINE_BYTES` 一致），超限抛 `LlmCallException(PARSE)`。这个改动很小，且不涉及兼容回退路径，风险低于 R-01。

## 7. R-06 / R-07：Jetty 排队请求与客户端数量（中高 / 中）

### R-06 排队请求无显式上限

`JettyHttpExecutor.createClient`（`:407-458`）只设了 `maxConnectionsPerDestination` 和 `setIdleTimeout(0)`，**没有** `setMaxRequestsQueuedPerDestination`。

Jetty 9.4 的默认值是 `maxRequestsQueuedPerDestination = 1024`（在 `jetty-client-9.4.53` 字节码的 `HttpClient.<init>` 里确认）。超出连接数的请求进入 `HttpDestination` 队列，每个排队的 `HttpExchange` 持有 `HttpRequest` → `StringContentProvider` → **完整的请求体 String**（`:359` 构造）。

按 1MB 提示词 × 1024 排队 = **单目的地址约 1GB**。

**触发条件**：并发数超过 `max-connections-per-destination`（默认 64，A104527 配的是 200），且请求体较大。这是「稳态高并发 + 长 prompt」场景。

**为什么压测没发现**：我只配了一种 timeout、没超过连接数上限，请求体也小。

**部分防护**：`ProviderGuard` 配了 `concurrency` 时会在更上游挡住，但 guard 默认不建实例（`AiLiteAutoConfiguration` 只在显式配置时创建），所以默认配置下这条上限不存在。

### R-07 客户端数量上限偏宽

`MAX_CLIENTS = 16`（`:64`），按 connect timeout 为 key 缓存客户端。未配 `ai-lite.http.jetty.threads` 时，每个客户端用 Jetty 默认 `QueuedThreadPool`（min 8 / max 200）。16 × 200 = **最多 3200 线程**。

有上限（挡住了无限增长），但过宽。实际消耗取决于用了几个不同的 `connect-timeout-ms`。

A104527 生产配了 `threads: 32` 和 `threads: 64`（dev/prod 不同），所以走的是固定池，这条影响较小。

## 8. 已确认不是问题的地方

这几条我专门验证过，避免报告只报坏消息、也避免你们去查不存在的问题。

### 8.1 没有慢性内存泄漏

所有场景连跑两遍，第二遍的 GC 后留存都是 `+0.0 MB` 或个位数：

| 场景          | 第一遍留存   | 第二遍留存       |
| ----------- | -------:| -----------:|
| 正常非流式       | +2.9 MB | **+0.0 MB** |
| 大分片流式       | +2.8 MB | **+0.0 MB** |
| 深嵌套 20000 层 | +0.1 MB | +0.0 MB     |
| 429 重试      | +0.0 MB | +0.0 MB     |
| 响应提前断开      | +0.0 MB | −0.0 MB     |

第一遍的增量是 JIT、类加载、Jetty 内部结构的**一次性**开销，不是每次调用都在漏。`inFlightRetries` 那个集合在 429 重试场景后也没留下东西。

### 8.2 线程增长是一次性扩容

线程从 21 涨到 49~82，看着吓人，但：

- 增量集中在 `HttpClient@...-=40`（Jetty 连接池按并发扩出来的，符合 `max-connections-per-destination: 200`）
- 同一场景跑第二遍：**+0**
- 所有故障场景跑完后再跑正常场景：线程不涨

`ai-lite-retry-=2` 是重试调度器，也是固定 2 条，不随调用次数涨。

### 8.3 深嵌套没有打死 Jetty 回调线程

这是我最担心的一条（Jetty 的 selector/回调线程是固定小池，打死会拖垮所有在途请求）。实测 200 轮 20000 层嵌套，线程数不变，堆不涨。

代码复核确认两条路径都有兜底：

| 路径  | 兜底位置                                                                                   |
| --- | -------------------------------------------------------------------------------------- |
| 非流式 | `thenApply` 的异常被 `whenComplete`/`handle` 转成 future 异常完成                                |
| 流式  | `JettyHttpExecutor.java:289` 的 `catch (Throwable)` → `completeExceptionally` + `abort` |

**但 R-02 仍然需要修**：兜底只是「不让它扩散」，`StackOverflowError` 本身仍然在解析线程上真实发生过。它被接住时的线程栈已经消耗殆尽，如果解析过程中还有别的帧需要栈，行为就不可预测。加一层显式的深度限制比依赖「外层恰好接住」更可靠。

## 9. 代码复核中已确认的其他事实

以下是读代码直接确认的，不依赖压测。子代理的静态分析仍在进行，覆盖本报告尚未涉及的路径，结果回来后补入本节。

### 9.1 `raw` 累积器只在 OpenAI Completions 里存在

我查了三个传输实现：

| 传输                           | 是否累积全文             |
| ---------------------------- | ------------------ |
| `OpenAiCompletionsTransport` | **有**（`raw`，`:93`） |
| `OpenAiResponsesTransport`   | 无                  |

所以 R-01 的修复范围比预想小——只改一个文件。但 A104527 生产配置的协议是 `openai-completions`，正好落在这个范围内。

### 9.2 没有任何体积上限

对 `OpenAiCompletionsTransport` 搜索 `MAX_`、`limit` 等常量，**一个都没有**。三个累积器 `raw`、`State.content`、`State.reasoning` 全部无界。相比之下 `JettyHttpExecutor` 是有上限的（`MAX_LINE_BYTES = 1MB`、`MAX_ERROR_BYTES = 64KB`），说明作者在传输层考虑过这个问题，但协议适配层没有延续。

`MAX_CLIENTS = 16`，按 connect timeout 缓存客户端；超过就抛配置错误而不是继续创建（`:396`）。这条避免「异常配置导致线程/selector 泄漏」，压测中没有发现问题。

### 9.4 已复核通过、确认有防护的路径

子代理做了静态排查，以下这些它读代码确认**有防护**，我也复核了关键几处：

### 9.5 一条经实测证伪的静态推断

子代理报告了一条「外层 `LlmCancelHandle` 永不解绑，长期持有整条 `AsyncRun`（含 transcript、apiKey 明文、完整回复）」，严重度标为「中 · 已确认缺陷」。

**我实测证伪了它。**

它引用的行号 `LlmGateway.java:775` 和 `:841` 确实有 `outerCancel.bindAbort(...)`，但这两行落在 **`RetryRun`（809–1208）** 里，不是它声称的 `AsyncRun`（1209 起）。`RetryRun` 有 `unbindOuter()`（`:1174`）负责解绑；`AsyncRun` 从头到尾**没有把自身绑到调用方句柄上**——它绑的是 `freshAttemptCancel`（`:1746`）里的轻量 `fresh` 句柄。

实测（`CancelHandleRetentionProbeMain`）：300 次调用、保存全部句柄 vs 不保存，GC 后堆占用差值：

| 入口                  | 保存句柄    | 不保存     | 差值          |
| ------------------- | -------:| -------:| -----------:|
| `oneAsync`          | 10.5 MB | 10.7 MB | **−0.2 MB** |
| `oneWithRetryAsync` | 10.1 MB | 10.0 MB | **0.0 MB**  |

两条入口都没有滞留。**这条不列入风险清单。**

这个例子说明静态分析的局限：行号归属错位会让「捕获了整个对象」这种判断成立得很像，但只有跑起来才分得清。

### 9.6 一条需要修正的预期

子代理指出 Jetty 9.4 默认用 `ExecuteProduceConsume` 策略：拿到可读事件后通过 `Executor.execute` 交给 `QueuedThreadPool` 工作线程执行。所以 `Response.Listener` 回调跑在**工作线程**上，不是 selector 线程本身。

这意味着「栈溢出会打死 selector」这个担忧不成立——会打死的是工作线程，由池补建。真正要担心的是 R-06 的排队和 R-07 的线程数上限。

实测侧证：压测中线程名前缀一直是 `HttpClient@...-=40`（工作线程）和 `ai-lite-jetty-*`（用户池），selector 线程数量稳定。

### 9.7 静态分析未覆盖的范围

它明确说了没读：`ai-lite-admin-api`、`ai-lite-prompt*`、`ai-lite-session-jdbc`、`ai-lite-session-redis`、`ai-lite-store-jdbc`、`ai-lite-executor-coroutines`、`ai-lite-executor-jdk21`、五种非 Jetty 传输、`SessionCompactor` 的摘要生成实现细节、`benchmark`。

本次分析聚焦 `ai-lite-llm` + `ai-lite-http-jetty`，上述模块不在范围内。

## 10. A104527 的真实调用形态（压测场景依据）

压测场景是按 A104527 的三种真实调用形态设计的：

### 10.1 工种清洗（最重）

`WorktypeCleanTaskService.driveLoop`（`bsplatform/bsp-web-core/.../WorktypeCleanTaskService.java:705`）是一条**自续递归链**：

```
driveLoop 循环取分片 → openLocalShard 发模型请求 → whenCompleteAsync 回调里
  → 再调用 driveLoop 取下一个分片
```

靠 `whenCompleteAsync(..., asyncExecutor)` 把下一轮推到线程池，**栈本身不涨**。

线程池配置（`WorktypeCleanExecutorConfig`）：

| 池                            | 核心/最大 | 队列  | 拒绝策略                   |
| ---------------------------- | ----- | --- | ---------------------- |
| `worktypeCleanExecutor`      | 3 / 3 | 8   | `AbortPolicy`          |
| `worktypeCleanAsyncExecutor` | 4 / 4 | 256 | **`CallerRunsPolicy`** |

**`CallerRunsPolicy` 在这里是个放大点**：队列满时任务在**提交者线程**上同步跑，而提交者可能是 Jetty 的回调线程。配合 R-01 的峰值膨胀，如果一个大响应的解析落在回调线程上，会把该线程占住更久。

分片 `SHARD_SIZE = 8`，每片一次模型调用。一次全量任务可能有几千片。

### 10.2 简历解析 / AI 简历（单次长耗时）

- `ResumeParseLlmModel.runAsync` 用 `oneAsync`（非流式）
- `GenerateAiResumeLlmModel.runAsync` 用 `oneByStreamAsync`，读超时 300 秒。注释写明用流式是为了避免上游 nginx 504

**`GenerateAiResumeLlmModel` 走的正是 R-01 那条路径**（OpenAI Completions 流式），所以它是这次峰值膨胀最可能的真实受害者。

### 10.3 压测入口已存在

A104527 里的 `LlmBenchService` + `LlmBenchHttpExecutor` 本来就是为压测写的：

- ThreadLocal 覆盖 transport（okhttp / jetty 可切）
- `LlmBenchUpstream` 把 URL 重定向到**只允许 127.0.0.1 / localhost / ::1** 的假服务
- 六个 profile 控制在途时长：15 / 30 / 45 / 60 / 75 / 90 秒
- `llm-bench.enabled=true` 才注册控制器

这意味着**不需要改 A104527 就能用它压本机的假服务**。
