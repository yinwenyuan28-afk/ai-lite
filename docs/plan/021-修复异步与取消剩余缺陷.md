## 0. 目标与边界

**一句话**：把「任何非正常路径都要给 future 一个终态」这条规矩补完，再收掉终态之后的尾巴和几处跨入口不一致。

| 目标 | 对应编号 |
| --- | --- |
| future 一定会结束（拒绝 / 停机 / 池满都不挂） | F-05、F-12、F-11 |
| 不会因同步递归把栈压爆 | F-09 |
| 结果已经给了，后面不该再冒字 / 不该留滞留任务 | F-04、F-10 |
| 三个入口、两条工具链、默认线程池的口径一致 | F-13、F-06、F-14 |

**不做**：3.2（NIO 与 HTTP 传输 F-17~F-30）、3.3（运行时配置 F-31~F-38）、P2 归档项；不改 `LlmCancelHandle` 所有权模型（P0 已定稿）；不重写 `SerialCallbackExecutor`（P0 已改成一任务一提交）。

**范围事实**：9 条全部经当前代码 grep 复核仍在；P0 之后 `LlmGateway` 最后一次改动就是 `efa08ec`。

## 2. 批次 A：拒绝路径也要给终态

### 2.1 F-05 排队等名额的人，永远没人叫他

**一句话目标**：载体池拒绝派发时，名额还了不算完，还得告诉排队的人「你没排上」。

**改前 / 改后（最小对比，`ProviderGuard.dispatchGrant()` / `dispatchReject()`）**

```java
// 改前：dispatchGrant():390-402
try {
    waiter.dispatcher.execute(() -> waiter.listener.onGranted(permit));
} catch (RejectedExecutionException ex) {
    permit.release();          // 名额还了 ……
}                              // …… 但 onGranted / onRejected 一个都没调

// 改后（示意）
} catch (RejectedExecutionException ex) {
    permit.release();
    waiter.listener.onRejected(new LlmCallException("出口保护载体池已拒绝", ex,
            LlmCallException.Kind.OVERLOAD));   // 在调用线程同步收敛
}
```

`dispatchReject():405-418` 的 catch 目前连日志都没有，同样补 `onRejected(reason)` 兜底。

**一个必须避开的坑**：只 catch `RejectedExecutionException`，不要扩大到 `RuntimeException`。若用户传的是内联 Executor，`listener.onGranted()` 自己抛的异常也会从 `execute()` 里冒出来，扩大捕获范围会造成「成功 + 拒绝」二次回调。这条在用例里要显式覆盖。

**落地清单**

| 位置 | 动作 |
| --- | --- |
| `ProviderGuard.dispatchGrant()` | catch 内 `permit.release()` 后同步 `onRejected(OVERLOAD)` |
| `ProviderGuard.dispatchReject()` | catch 内同步 `onRejected(reason)` + 一条 warn |
| `ProviderGuard` 类注释 `:33` | 补一句「拒绝路径在调用线程锁外同步回调」，保持既有线程纪律 |

**验收用例（`ai-lite-llm/src/test/.../guard/ProviderGuardTest`）**

| 用例 | 断言 |
| --- | --- |
| `rejectedDispatcherStillCallsOnRejected` | 排队 waiter + 拒绝型 dispatcher → `onRejected` 恰好一次、`permit` 已回流 |
| `grantDispatcherRejectionConvergesGatewayFuture` | 经 `LlmGateway.oneAsync` → future 在 5s 内异常完成，Kind=OVERLOAD |
| `inlineDispatcherListenerExceptionIsNotTreatedAsRejection` | 内联 dispatcher 下 listener 抛错，不触发二次 `onRejected` |
| `expireWaiterRejectionAlsoConverges` | 排队超时路径同样收敛 |

**风险**：`onRejected` 同步跑在 `dispatcher.execute` 的调用线程，可能就是 guard 的交接线程；网关的 `fail(...)` 会写调用记录。需确认 `fail` 不重入 guard 锁（当前回调纪律已要求锁外执行，实施时复核一次）。

### 2.2 F-12 说好「异步入口返回 future」，池满时却直接抛

**一句话目标**：`resumeAsync` 无论池多满，都必须返回一个 future；失败放在 future 里，不砸到调用线程。

**改前 / 改后（最小对比，`AgentSessionLoop.resumeAsync()`）**

```java
// 改前：:280-281
CompletableFuture<Prepared> prepared = CompletableFuture.supplyAsync(
        () -> prepare(userId, sessionId, call, lifecycles, newUserTurns), executor.io());
//    execute 被拒 → 同步抛 RejectedExecutionException，下面这行根本走不到
final CompletableFuture<ResumeResult> future = prepared.thenComposeAsync(...);

// 改后（示意）
CompletableFuture<Prepared> prepared;
try {
    prepared = CompletableFuture.supplyAsync(
            () -> prepare(userId, sessionId, call, lifecycles, newUserTurns), executor.io());
} catch (RejectedExecutionException ex) {
    return failedFuture(new LlmCallException("会话恢复任务被拒绝", ex,
            LlmCallException.Kind.OVERLOAD));
}
```

正确范式在同一仓库已有：`Workflow.adapt():503-523` 显式包了这一层。

**待先验证的一点**：`thenComposeAsync` / `thenApplyAsync` 的宿主线程被拒时，JDK 8 到底是「同步抛」还是「返回异常完成的 future」。017 台账按同步抛记录，但**先写一条用例确认**，再决定要不要给整条链再包一层 try/catch；不要凭猜测两边都加。

**落地清单**

| 位置 | 动作 |
| --- | --- |
| `AgentSessionLoop.resumeAsync()` `supplyAsync` | 包 `try/catch(RejectedExecutionException)` → `failedFuture` |
| 同方法 `thenComposeAsync` 宿主 `executor.io()` | 按用例实测结果决定是否同样包一层 |
| `thenApplyAsync(... finish ...)` 宿主 | 同上 |
| `Workflow.adapt()` | 只作参照，不改 |

**验收用例（`ai-lite-agent/src/test/.../session/AgentSessionLoopAsyncTest`）**

| 用例 | 断言 |
| --- | --- |
| `resumeAsyncReturnsFutureWhenIoPoolRejects` | 拒绝型 executor → 方法正常返回 future，`get()` 抛 `ExecutionException`，cause=Kind.OVERLOAD |
| `resumeAsyncDoesNotThrowFromCallerThread` | 调用线程不出现 `RejectedExecutionException` |
| `thenApplyHostRejectionKeepsFutureContract` | 第二阶段拒绝也只体现在 future 里 |

**风险**：`failedFuture` 需与项目既有的 `Workflow.failedFuture` 口径一致（JDK 8 无 `CompletableFuture.failedFuture`，需手写 `completeExceptionally` 的辅助方法或复用现有工具）。若引入新辅助方法，放在 `internal` 包，不进公开 API。

## 3. 批次 B：F-09 工具循环改成蹦床推进

**一句话目标**：一轮接一轮不再靠「回调里再调自己」压栈，改成「有人要推进就记一笔，一个人循环处理」。

**现在的链**（同步完成型 transport / ToolExecutor 下全部内联）：

```text
next() → startRound() → future.whenComplete(内联) → toolFuture.whenComplete(内联) → next() → …
```

每轮压两层栈，`maxRounds` 大时栈溢出。`Workflow.advance()` 与 `AgentLoop.drainLoop()` 已用 `wip` 蹦床解决，网关的 `AsyncRun` 没有。

**改后（结构示意，照 [008-Workflow异步执行器](008-Workflow异步执行器.md) §2 的 wip 范式）**

```java
private final AtomicInteger wip = new AtomicInteger();
private volatile Runnable pending;

/** 不再直接 next()，只登记「要推进」；已在 drain 中的人负责继续循环。 */
private void signalNext(Runnable task) {
    pending = task;
    if (wip.getAndIncrement() == 0) {
        do {
            Runnable t = pending;
            pending = null;
            if (t != null) { t.run(); }
        } while (wip.decrementAndGet() != 0);
    }
}
```

`toolFuture.whenComplete` 尾部的 `next()` 改为 `signalNext(this::next)`；`startRound` 的 guard 快速路径 `onGranted` 同样收编。**终态检查、cancel 检查、`recordTerminal` 恰好一条**这些现有语义一条都不能丢——它们目前在 `next()` 开头和工具回调尾部，搬进蹦床时要逐条对照。

**落地清单**

| 位置 | 动作 |
| --- | --- |
| `LlmGateway.AsyncRun` | 新增 `wip` / `pending` 字段与 `signalNext(...)` |
| `AsyncRun.next()` | 保留原有终态、cancel、guard 分支；入口改由 `signalNext` 驱动 |
| `startRound()` 的 `future.whenComplete` 工具分支尾部 | `next()` → `signalNext(this::next)` |
| `guard.acquireAsync` 的 `onGranted` 快速路径 | 收编进同一推进入口，避免两条路径并发 drain |
| `maxRounds` | 仍设硬上界（防御性，不作为主修法） |

**验收用例（新增 `ToolLoopTrampolineRegressionTest`）**

| 用例 | 断言 |
| --- | --- |
| `synchronousTransportWithLargeMaxRoundsDoesNotOverflow` | fake transport 同步完成、`maxRounds=2000` → 正常结束，无 `StackOverflowError` |
| `roundOrderAndRecordCountUnchanged` | 每轮记录恰好一条、顺序与改前一致 |
| `cancelDuringDrainStopsImmediately` | 蹦床循环中取消 → 不再发起下一轮 |
| `guardQueuedPathDoesNotDoubleDrain` | 排队交接与同步完成混合，不出现两轮并发 |

**风险（本批次最高）**：推进结构是所有 `toolLoopAsync` / `AgentLoop` / `Workflow` 共用的底座。必须跑全量 `mvn verify`，尤其 `LlmGatewayToolLoopRecordTest`、`LlmGatewayAsyncTest`、`AgentLoopAsyncHardeningTest`、`AgentLoopIoModeTest`、`WorkflowHardeningTest`。若回归难以收敛，退而求其次：只在检测到同步重入时把下一轮投递到 `executor.io()` 切栈（改动小，但会引入新的拒绝路径，需按批次 A 的口径一并收敛）。

## 4. 批次 C：F-11 停机时给在途 future 一个明确终态（顺手修）

**一句话目标**：不是怕挂住（复核已确认影响面有限），而是让停机时的在途调用拿到「服务正在关闭」而不是静默超时。

**推荐方案（约 20 行，复用 A 的收敛入口）**

```java
// LlmGateway：只登记「正在退避」的 RetryRun
private final Set<RetryRun> inFlightRetries = ConcurrentHashMap.newKeySet();

/** 容器关闭时调用：先收敛在途，再交给 scheduler 的 shutdownNow 回收线程。 */
public void shutdown() {
    LlmCallException closing = new LlmCallException("服务正在关闭", null,
            LlmCallException.Kind.TRANSPORT);
    for (RetryRun run : inFlightRetries) {
        run.convergeShutdown(closing);      // result.completeExceptionally + 取消本代 ScheduledFuture
    }
}
```

- `RetryRun.scheduleRetry()` 成功后登记，`runScheduledAttempt()` / `convergeFailure()` 退出时注销。
- `AiLiteAutoConfiguration.aiLiteGateway()` 显式写 `destroyMethod = "shutdown"`；Spring 按依赖关系销毁，网关先于它依赖的 `aiLiteRetryScheduler` 关闭——**此顺序需写一个装配测试确认**，不确认就不要上线这一步。
- 手工构造网关走 `RetryScheduler.shared()`（daemon、进程级、不随单网关关闭），本来就没有 F-11，无需改动。

**验收用例**

| 用例 | 断言 |
| --- | --- |
| `shutdownConvergesBackoffFuture` | 退避中调 `gateway.shutdown()` → future 异常完成、cause 消息含「服务正在关闭」 |
| `shutdownIsIdempotent` | 重复调用不产生第二条终态记录 |
| `normalCompletionUnregistersRetry` | 正常完成后注册表为空，shutdown 不误伤 |

**可跳过条件**：若批次 A 没有抽出可复用的收敛入口，或装配销毁顺序无法确认，本批次直接跳过并在 017 / 020 留档注明，不阻塞其它批次。

### 12.2 实测踩坑（与计划不一致的地方）

1. **F-12 的「待验证疑点」已证掉。** 写了一个独立探针实测 JDK 8：`supplyAsync` 宿主拒绝**同步抛**；
   `thenComposeAsync` / `thenApplyAsync` 宿主拒绝**只让返回的 future 异常完成、不抛**。
   所以只有 `supplyAsync` 一处需要包，计划里「按实测结果决定是否给整条链再包一层」的疑问已回答。
2. **F-09 的失败形态与计划预期不同，且更糟。** 计划预期 `StackOverflowError`；实测是它被
   `whenComplete` 的回调层**吞掉后 future 永久挂起**，只表现为超时。用不同栈大小的线程隔离验证：
   512KB 栈下 400 轮挂住，8MB 栈下 2000 轮 20ms 正常——确认是纯栈深度问题。
3. **F-05 的「不扩大到 RuntimeException」是必须的。** 内联载体下 `execute()` 会同步跑完
   listener，listener 自己抛的异常会从 `execute` 冒出来；此时 `onGranted` 已经执行过，
   再补 `onRejected` 就是双回调。已写成用例 `inlineDispatcherListenerExceptionIsNotTreatedAsRejection`。
4. **F-11 的 `@Bean(destroyMethod = "shutdown")` 其实不是必需的。** 实测 Spring 默认的
   `(inferred)` 策略本来就会推断到同名方法。真正起作用的是登记表与 `convergeShutdown`。
   注解保留作为显式声明，但已把这点写进代码注释与提交说明，避免后人误以为删了它会坏。
5. **F-10 无法复现。** 试了三种注入（跳过锁内复查、把 `schedule()` 之后卡住撑开窗口、
   拉长退避让任务留在延迟队列），都无法构造出滞留。原因是 `schedule()` 返回后的锁内复查
   与 `claimTerminalLocked` 的两道撤销已经把窗口盖住。按「已知正确行为」留守护用例。
6. **F-14 的判断依据不能只看「有没有传执行器」。** 手工构造时调用方常显式传
   `DirectExecutorProvider`，那同样是内联。改成按 `provider instanceof DirectExecutorProvider`
   判断。第三方执行器无法可靠判定，一律按原样使用——猜错反而会把记录线程搞乱。
7. **F-14 改了记录时序，连带 8 处旧用例要改。** 那些用例假设「`one()` 返回时记录已写入」。
   统一改成 `store.awaitRows(n)` + 按轮号排序读取。这本身是个有价值的信息：
   **升级说明里必须写清「手工构造场景记录不再内联」**（已写进 CHANGELOG 升级必读第 4 条）。
