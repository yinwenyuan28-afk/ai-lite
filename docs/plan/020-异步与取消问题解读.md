## 2. A 组：会让调用方卡死或崩

### F-05 排队等名额的人，永远没人叫他

**一句话**：出口限流开启后，请求要排队等名额。线程池拒绝派发时，代码把名额还了，却没告诉排队的人「你没排上」——那个人的 `oneAsync` 就永远等不到结果。

你会写的代码只有这一行，但并发打满时它可能永远不返回：

```java
CompletableFuture<LlmResult> f = gateway.oneAsync(call);  // guard 已开启、排队中
f.get(5, TimeUnit.SECONDS);                              // 抛 TimeoutException
```

改前的关键几行（`ProviderGuard.java:390-418`）：

```java
try {
    waiter.dispatcher.execute(() -> waiter.listener.onGranted(permit));
} catch (RejectedExecutionException ex) {
    permit.release();          // 名额还了 ……
}                              // …… 但 onGranted / onRejected 一个都没调
```

`AsyncRun.next()` 的注释写得很清楚：它的下一段全靠 `onGranted` 或 `onRejected` 唤醒。两条路都断了，future 就没人 complete。`dispatchReject` 的 catch 更直接，连日志都没有。

**修法**：拒绝时在调用线程同步调 `waiter.listener.onRejected(reason)`，让网关收敛成 OVERLOAD（不是挂起）。

### F-11 停机时，正在退避的请求被「人间蒸发」

**一句话**：重试的两次尝试之间会睡一会儿（退避），这个「睡」交给一个定时任务。停机时这个任务被直接丢掉，而网关的 future 只等它来唤醒。

#### 先说清楚「应用停机」是什么

**停机 ≠ 断电，进程没有瞬间消失。** 它就是你亲手做过的动作：本地按 `Ctrl+C`、IDE 点红色停止按钮、`kill <pid>`、K8s 滚动发布给旧 Pod 发退出信号、`@SpringBootTest` 跑完用例。之后 Spring Boot 会进入几秒到几十秒的收尾过程：进程还活着、线程还在跑、已接进来的请求还要处理完，只是 Spring 开始**逐个关闭自己创建的 Bean**（线程池、连接池、调度器）。

在这个项目里，「容器停机」这五个字翻译成代码就是一句方法调用，因为自动装配里写了（`AiLiteAutoConfiguration.java:201`）：

```java
@Bean(name = "aiLiteRetryScheduler", destroyMethod = "shutdownNow")
```

Spring 关闭时看到 `destroyMethod`，就去调 `retryScheduler.shutdownNow()`。**没有其它魔法。**

#### 最小示例与实际输出

```java
ScheduledThreadPoolExecutor pool = new ScheduledThreadPoolExecutor(1);
pool.setExecuteExistingDelayedTasksAfterShutdownPolicy(false);   // RetryScheduler.java:55
CompletableFuture<String> f = new CompletableFuture<>();

pool.schedule(() -> f.complete("第二次尝试的结果"), 1, TimeUnit.SECONDS);  // 安排「1 秒后再试」

System.out.println("停机前 f 完成了吗? " + f.isDone());
List<Runnable> dropped = pool.shutdownNow();     // ← 这就是「停机」在代码里发生的事
System.out.println("被丢掉的任务: " + dropped.size());
Thread.sleep(1500);
System.out.println("停机后 f 完成了吗? " + f.isDone());
```

```
停机前 f 完成了吗? false
被丢掉的任务: 1
停机后 f 完成了吗? false
```

把 `shutdownNow()` 换成 `shutdown()`（并允许已排队的延迟任务跑完），同样的代码输出 `true, value = 第二次尝试的结果`。**F-11 的全部机制就是：唯一会完成 `f` 的那个任务被扔了，而没人补一句通知。**

#### 六个步骤（含 future 状态）

| 步 | 发生了什么 | `f` 的状态 |
| --- | --- | --- |
| ① | 调 `oneWithRetryAsync`，拿到 `f` | 未完成 · 正常 |
| ② | 首次请求 429，`scheduleRetry():941` 安排「30 秒后再试」 | 未完成 · 等定时任务 |
| ③ | 按 Ctrl+C / 发布重启，进程收到退出信号 | 未完成（进程还活着） |
| ④ | Spring 容器 `close()`，逐个调 Bean 销毁方法 → `shutdownNow()` | 未完成 |
| ⑤ | `RetryScheduler.java:55` 让延迟任务被直接丢弃：不执行，也不通知 | 未完成 |
| ⑥ | 再没有任何代码会调 `f.complete(...)` | **永远未完成** |

#### 三个朴素问题

- **都要关了，挂住有什么关系？** 见下面「严重度复核」：**多数情况下确实关系不大**。进程退出后 JVM 一起消失，`f` 与 daemon 线程都不复存在，客户端也有超时兜底。真正剩下的只是「语义不完整」——停机时没给在途调用一个明确终态，日志里缺一条失败记录。
- **为什么 `shutdownNow()` 不顺便通知 future？** 它只认识「任务」，不认识 `future`。`f` 是网关自己 new 的普通对象，定时任务只是恰好在 `run()` 里会调 `f.complete(...)`。任务被扔掉 = 唯一写着这行代码的纸条被撕了。这和 F-01 是同一个道理换了个场景。
- **那 `f` 还有别的完成路径吗？** 没有。`scheduleRetry()` 只在**提交被拒绝**时才 `convergeFailure`（`:947-955`）；提交成功之后，收敛全靠 `runScheduledAttempt():973` 里的 `startAttempt()` 或 `:988` 的 deadline 失败。任务被丢弃，两条路同时断了。

#### 严重度复核（2026-11-06，用户提出「感觉问题不大」）

复核后**同意降级**，理由有三：

1. **上一轮的论证把停机窗口说宽了**：Spring Boot 2.3+ 的 `server.shutdown` 默认是 `immediate`，`graceful` 必须显式配 `server.shutdown=graceful` 才生效（`Shutdown.IMMEDIATE` 为默认；`WebServer.shutDownGracefully()` 默认实现直接返回 `IMMEDIATE`）。本仓库是 starter，不带任何 `server.shutdown` 配置。默认停机几乎不等待在途请求。
2. **没有持续损害**：进程退出 → JVM 消失 → `f` 与 daemon 线程一起没了，不存在内存泄漏或线程泄漏；不会发起第二次 HTTP，也不会重复计费；客户端有超时兜底。停机是低频事件，且只有恰好落在退避窗口内的请求受影响。
3. **宿主配了 graceful 也不改变结局**：最终仍要退出，差别只是多等一小段时间。Bean 销毁与 web server 停止的先后顺序未核实，列为待验证疑点，不作为论据。

剩下值得做的只有**语义一致性**：停机时给在途 future 一个明确的「服务正在关闭」异常，让调用方拿到错误而不是超时、让日志与指标能收口。属于 P2/P3，不单独排期，跟 F-05 / F-12 的「非正常路径也要给终态」一起顺手做即可。

另一个更容易踩到的场合是**测试**：`LlmGatewayAsyncRetryTest`、`LlmGatewayAsyncRetryParityTest` 等 6 个测试类在 `@After` 里调 `scheduler.shutdownNow()`，此时 JVM 还活着、JUnit 继续跑下一个用例。若将来某个用例没等 future 完成就结束，会留下挂起的 future。当前 1074 个用例全绿，说明尚未暴露——这是「将来可能踩」，不是现存故障。

#### 根因与修法

两处配置叠加（`RetryScheduler.java:55` + `AiLiteAutoConfiguration.java:201`）：

```java
executor.setExecuteExistingDelayedTasksAfterShutdownPolicy(false);  // 停机丢弃延迟任务
@Bean(destroyMethod = "shutdownNow")                                // 直接强关
```

**修法二选一**：① 停机时对在途 future 统一 `completeExceptionally(停机异常)`，让调用方立刻拿到明确错误（推荐，语义最清楚）；② 改优雅关闭，让延迟任务正常触发、由 `runScheduledAttempt` 检查 `terminal` 后收敛。

### F-12 说好「异步入口返回 future」，池满时却直接抛异常

**一句话**：`resumeAsync` 的契约是「一定返回一个 future，失败也放在 future 里」。但 `CompletableFuture.supplyAsync` 在提交任务被线程池拒绝时，是**在调用线程上同步抛**的。

```java
// 期望：拿到 future，再等它异常完成
CompletableFuture<ResumeResult> f = sessionLoop.resumeAsync(...);   // ← 抛到这里
f.exceptionally(...);                                              // 根本走不到
```

当前代码（`AgentSessionLoop.java:281`）没有包这一层：

```java
CompletableFuture<Prepared> prepared = CompletableFuture.supplyAsync(
        () -> prepare(...), executor.io());        // execute 被拒 → 同步抛
```

同一个仓库里 `Workflow.adapt():523` 已经显式捕获过这个异常，这里漏了。`thenApplyAsync` 落在同一个池上，宿主线程拒绝时同样会漏。

**修法**：包 `try/catch (RejectedExecutionException)`，返回一个 `failedFuture`；`thenApplyAsync` 的宿主线程同样处理。

### F-09 工具循环的每一轮都叠在上一轮的调用栈上

**一句话**：如果传输层和工具执行器都是「调用即完成」型，`future.whenComplete` 会**当场**执行，于是下一轮在上一轮的回调里发起，一轮压一层，轮数够多就 `StackOverflowError`。

```java
gateway.toolLoopAsync(call, tools, 10_000)   // transport / ToolExecutor 都是同步完成型
// next → startRound → whenComplete(内联) → toolFuture.whenComplete(内联) → next → …
```

`Workflow` 和 `AgentLoop` 都有 `wip` 蹦床（用计数器把递归转成循环），只有网关的 `AsyncRun` 没有。它的 `next()` 是直接调用的。

**修法**：`AsyncRun.next()` 改成 `pendingOutcome + wip` 蹦床；或先给 `maxRounds` 设一个硬上界挡住最坏情况。

## 3. B 组：结果不干净，但不会卡死

### F-04 结果都返回了，字还在继续冒

**一句话**：`callback.mode=io` 下，`onDelta` 是排队的。队列溢出或 `future.cancel(true)` 收敛终态时，代码把 result 完成了，却没把队列关掉——排在里面的 delta 照样一个个执行。

```java
CompletableFuture<LlmResult> f = gateway.oneByStreamAsync(call, System.out::print, null);
f.cancel(true);                 // 调用方已经结束
// 控制台还在打印 "你好" "世界" ……  —— 终态之后的回调
```

`failOverload()`（`:1301`）和 `cancelledByFuture()`（`:1553`）都不调 `barrier.close()`；`onDelta` 的包装也不检查 `closed`。取消监听那条路本可能兜住，但它开头 `if (result.isDone()) return;` 直接返回了。

**修法**：收敛前先 `closeBarrier()`；`onDelta` 包装在 `closed` 之后直接丢弃。

### F-10 取消退避时，撤掉的是一个早就跑完的任务

**一句话**：`scheduledRetry` 这个字段只存「最后写进去的那一代定时任务」。零延迟 transport 下，第 1 次尝试的调度可能**后写**、覆盖掉第 2 次尝试的，于是取消时 `cancel` 的是旧的那个。

```text
attempt1 定时 S1 已触发
attempt2 定时 S2 排队中（Retry-After: 30s）
scheduleRetry(attempt1) 后写字段 → scheduledRetry = S1（错的）
cancelFromOuter() → S1.cancel(false)（早已触发，no-op）
S2 仍留在延迟队列，整个 RetryRun 被它引用 30 秒
```

根因：`retryScheduler.schedule(...)` 在 `synchronized (this)` 之外，返回后才进锁写字段（`:937-964`），两代之间没有代际标识。

**修法**：`schedule()` 移进锁内；或给每代 `ScheduledFuture` 附 generation，`runScheduledAttempt` 用 CAS 只清自己那一代。

### F-13 协程重试不认服务端的「等会儿再来」

**一句话**：Java 两个重试入口都读 `Retry-After`，只有协程入口不看，429 时按自己的指数退避猛打。

```text
服务端：429 + Retry-After: 30
Java oneWithRetry / oneWithRetryAsync  → 等 30 秒
LlmCoroutines.oneWithRetry             → 等 1 秒、2 秒、4 秒 ……
```

当前代码（`LlmCoroutines.kt:78`）只有一行：

```kotlin
var wait = policy.delayMs(attempt)      // 没读 ex.retryAfterMs
```

Java 两侧是 `min(retryAfterMs, maxBackoffMs)`。**修法**：抽 `RetrySupport.backoffMs(policy, failure, attempt)` 给三个入口共用，避免三份实现继续漂移。

## 4. C 组：跑错线程 / 拖慢系统

### F-06 `PARALLEL` + io 时，钩子跑在错误的线程上

**一句话**：配了 `callback.mode=io` 就是要求「钩子和回调都在 `ai-lite-callback-*` 池上」。串行链记得传 `cbExec`，并行链漏了。

```java
// 串行链（对）：
chain = chain.thenComposeAsync(..., cbExec);
// 并行链（错）：
return convergeFailFast(futures)
        .thenApply(...)      // 没传 cbExec
        .thenRun(...);       // 也没传 → 落在工具载体线程
```

后果是 `afterTool` 钩子和消息写回跑到工具线程上，回调策略的线程契约在 `ToolRunMode.PARALLEL` 下失效。**修法**：两处补 `cbExec`，并补一条线程名断言的用例。

---

### F-14 没传 executor 时，写库直接压在 I/O 线程上

**一句话**：手工构造网关时 `executor` 传 null，会退化成 `DirectExecutorProvider`——它的 `io()` 就是 `command.run()`，所谓「异步落库」变成在 OkHttp Dispatcher 线程上同步执行 JDBC。

```java
new LlmGateway(resolver, transports, jdbcStore, null, null);
// this.executor = new DirectExecutorProvider()   （LlmGateway.java:104）
// logger.record(row) → executor.io().execute(task) → task.run() 就在此线程
```

`AsyncLlmCallLogger` 的任务体还 `catch (Throwable)` 吞掉存储异常、线程池拒绝只打 warn，于是停机和拒绝时记录**静默丢失**，没有任何计数。

**修法**：默认也给一个有界守护池；`record` 先入有界队列由专用单线程消费；丢弃计数指标化 + shutdown 时 drain。

## 5. 一句话记住这 13 条

> **四条已修别再看。剩下九条里，A 组三条是「有人该通知却没通知」（F-05、F-12）或「一轮压一轮」（F-09）；B 组三条是「该关的没关、该撤的撤错、该等的没等」；C 组两条是「活儿跑错了线程」；F-11 影响面有限，降级为顺手修。**

```text
F-13 → F-06 → F-14     一致性收尾：三入口共用退避、并行链补 cbExec、默认给真线程池
```
