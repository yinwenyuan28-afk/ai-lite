# 修复运行时配置与目录缺陷（F-31 ~ F-34、F-36、F-37 已修；F-35/F-38 另议）

> **实施结果**：F-31、F-32、F-33、F-34、F-36、F-37 已修复并有回归用例；
> F-33 的实现方案在实施时从「唯一索引」改为「应用层加锁」，理由见 §2.6。
> F-35（接口鉴权）与 F-38（解析路径契约）需要产品决策，未动。

> **定位**：只处理[基础能力代码审查](017-基础能力代码审查.md)第 3.3 节那 8 条。不碰单次调用、异步取消、NIO 传输，不改管理页前端，不新增依赖。
> 
> **先说结论**：这 8 条**不是同一个难度**。3 条几行代码就能改（F-31、F-36、F-37），2 条中等（F-32、F-34），1 条要动表结构并写升级说明（F-33），剩下 2 条根本不该混进「顺手修一批」里（F-35 要定部署方案，F-38 要定公开 API 的语义）。
> 
> **本文写法**：每条先列审查原话、再贴源码位置、再给最小复现的线程时序或数据流，最后才说怎么改。核实不过关的条目不硬改，写明为什么。

## 1. 逐条核实

### F-31 缓存失效竞态 —— 属实，时序可复现

**审查原话**：`invalidate()` 不持锁，`load()` 在 `synchronized(this)` 内 `read()` 后**无条件写回**并重置 TTL。

**源码位置**：`JdbcRuntimeCatalog.java:211-214`（`invalidate`）、`:509-524`（`load`）；`JdbcCallBodyPolicy.java:86-98`（`level`）、`:132-148`（`save`）、`:153-156`（`invalidate`）。

**两个线程的实际交错**：

| 顺序  | 线程 A（读）                                        | 线程 B（管理页保存）          | 共享状态             |
| --- | ---------------------------------------------- | -------------------- | ---------------- |
| ①   | 进 `load()`，拿到锁                                 | —                    | snapshot 空       |
| ②   | 执行 `read()`，从库里读出旧值（3 次查询中）                    | —                    | snapshot 空       |
| ③   | —                                              | 写完库，调 `invalidate()` | snapshot = null  |
| ④   | `snapshot = loaded`（旧值），`expiresAt = now + 5s` | —                    | **缓存是旧值，TTL 全新** |

结果：管理页刚保存完，本机最多再返回 5 秒旧配置。`cacheSeconds` 配多大就错多久，而且这 5 秒是从第 ④ 步重新算的，不是从保存时刻算。

`JdbcCallBodyPolicy` 更直接：`level()` 和 `save()` 用的都是普通 `volatile` 字段，`level()` 里「读库 → 写缓存」两步之间没有任何互斥，同样能写出旧值配新 TTL。

**唯一需要修正审查措辞的地方**：审查写「`invalidate()` 完全失效」不准确——单线程下它工作正常，只在读库与写入并发时被覆盖。批量改配置的场景（管理页保存完立刻刷新列表）就会撞上。

### F-32 三表快照无事务、写侧多语句非原子 —— 属实，且写侧比读侧更严重

**源码位置**：读侧 `JdbcRuntimeCatalog.java:526-569`，三条独立 `jdbc.query`；写侧 `saveOverlay():221-234`、`saveBinding():483-494`、`JdbcCallBodyPolicy.save():132-148`。

读侧：默认 autocommit 下每次 `query` 是独立事务，三条查询分别看到三个时刻的库。可能读到「绑定指向的模型行已被删除」或「覆盖表 DELETE 已提交、INSERT 还没做」的中间态。

写侧：`saveOverlay` 和 `saveBinding` 都是 `DELETE` 再 `INSERT`，两条语句各自提交。若 `INSERT` 失败（约束冲突、列超长、连接断在中间），`DELETE` 已经生效，**这条配置直接消失**，且管理页看到的是一次 500 错误，不知道数据已经没了。这是这批里唯一会造成数据丢失的缺陷，也是最该先修的。

**顺带发现**：`JdbcPromptStore` 已经用 `TransactionTemplate` 处理同类问题（`JdbcPromptStore.java:37`、`:64`），装配层也已经把 `PlatformTransactionManager` 传给它。所以这里不是要引入新机制，是把同项目已有的做法补齐。

### F-33 模型表缺逻辑唯一键 —— 属实，但改法要绕开老库里的存量重复行

**源码位置**：`ai-lite-catalog.sql:1`（注释明写「只有主键，不建额外唯一索引」）、`:30-49`（模型表定义）；`JdbcRuntimeCatalog.java:284-300`（先查再插）、`:423-428`（`UPDATE ... WHERE PROVIDER_ID=? AND MODEL_ID=?`）、`:553`（`>=` 平局取后读）。

三处后果都能对上：

1. 两个请求同时 `adopt` 同一对 `(PROVIDER_ID, MODEL_ID)`：`findModel` 都没查到（缓存里也没有），`COUNT(*)` 都是 0，都执行 `INSERT`，插出两行。
2. 之后 `saveCapabilities` / `setReady` 的 `WHERE PROVIDER_ID=? AND MODEL_ID=?` 一次更新**全部重复行**，看起来「没问题」；但 `read()` 只 `put` 一个进 Map，另一行永远读不到，于是「我明明保存了、刷新又变回去」。
3. `read()` 的 `SELECT` 没有 `ORDER BY`，数据库返回顺序未定义；`>=` 让后读到的那行覆盖先进去的。同一毫秒的 `UPDATE_TIME` 相等时，取哪行取决于驱动。

**难度来自升级**：用户库里可能已经有重复行了，直接 `CREATE UNIQUE INDEX` 会失败。所以这条不能只改 SQL 文件。

### F-34 能力参数 NULL 静默降级 —— 属实，七项里四项真有问题

**源码位置**：`ModelResolver.java:290-318`（`toConfigModel`）、`:387-396`（`resolve` 里的默认值）；`CatalogModel.java:141`（`isReasoning()` 返回 `boolean`）。

`toConfigModel` 对前七项只取数据库，数据库列是 `NULL` 时的实际落点：

| 列                 | NULL 时变成             | 后果                                                   |
| ----------------- | -------------------- | ---------------------------------------------------- |
| `REASONING`       | `false`              | `LlmThinking.clamp` 把思考档压到 off，用户配了 high 也不生效        |
| `CONTEXT_WINDOW`  | `0`                  | `ContextBudget.triggerTokens` 返回 0，预算检查与自动压缩**整条跳过** |
| `MAX_TOKENS`      | `8192`               | 与 YAML 默认值相同，基本无害                                    |
| `INPUT_MODES`     | `["text"]`           | `acceptsImage` 为 false，图片消息被拒                        |
| `THINKING_FORMAT` | `"reasoning-effort"` | YAML 里写 `chat-template` 的同名模型被忽略                     |

关键是 `REASONING` 这一列在 `CatalogModel` 里是原始 `boolean`，**表达不了「没填」**，所以只能靠改类型或加一个可空访问器，这是这条唯一的麻烦点。其余四项用的都是 `Integer` / `String` / `List`，本来就能携带 null。

触发条件不是「模型没配」，而是「**行存在但没填参数**」：`insertModelIfAbsent` 建行时所有能力参数都是 NULL（`JdbcRuntimeCatalog.java:294-297`），只要有人对这个行调 `setReady(true)`，就得到一个「已启用、参数全空」的模型，而管理页上 `READY` 显示绿色。

### F-35 管理接口无鉴权 —— 属实，但这不是一批代码能解决的问题

**源码位置**：`AiLiteAdminAutoConfiguration.java:32-42`（装配条件只有「Servlet 应用 + 有 DispatcherServlet + 开关打开」）；`AdminController` 全类没有任何鉴权注解、拦截器或 `Filter`。

能做的事很多：改 `API_KEY`（把流量引到任意端点）、改 `BASE_URL`、放行未就绪模型、发起真实模型请求、读调用记录和正文。

**为什么不算「好解决」**：加一个 token 校验只需要几十行，但真正要定的是——token 从哪来（配置项？环境变量？）、没配 token 时是拒绝启动还是只告警、是否要额外支持只读角色、反向代理已有认证时怎么关掉这层。这些定了才好写。所以放在最后一节单独议。

### F-36 异常原文回显 —— 属实

**源码位置**：`JdbcRuntimeCatalog.java:616`、`:642`、`:669`（三处 `+ ex.getMessage()`）；`AdminController.java:883-889`（`badRequest` 原样回显 `ex.getMessage()`）。

Jackson 的 `JsonParseException.getMessage()` 会带出错位置的源文本片段（默认 `INCLUDE_SOURCE_IN_LOCATION`）。这些列里存的是请求头、附加请求体——**可能含自定义鉴权头**。叠加 F-35 的无鉴权，任何人都能构造一条坏 JSON 再读响应体。

改法很小：消息里只保留「表名 + 行列定位 + 列名」，不拼 `ex.getMessage()`，也不把原始异常挂成 cause 往外抛（`IllegalStateException(..., ex)` 里的 cause 不会被 `badRequest` 输出，但会进日志，那是有意的，保留）。

### F-37 档位显示与实际不一致 —— 属实，而且「照建议直接改注解」会引出更糟的问题

**源码位置**：`AiLiteCatalogAutoConfiguration.java:111-117`。

```java
@Bean
@ConditionalOnMissingBean(CallBodyPolicy.class)   // 条件类型
public CallBodySettings aiLiteCallBodyPolicy(...)  // 返回类型
```

条件类型和返回类型不对称。用户自己声明一个 `CallBodyPolicy` Bean 后，这个 Bean 不创建，于是 `AiLiteAdminAutoConfiguration.java:79` 的 `ObjectProvider<CallBodySettings>` 取到 null，管理页档位恒为 `none`，`PUT` 抛「调用记录档位不可用」——而网关实际用的是用户的策略。正是 `CallBodySettings.java:11-12` 想避免的「显示与实际不一致」。

**但审查给的建议「条件改 `@ConditionalOnMissingBean(CallBodySettings.class)`」不能直接用**。改了以后，用户有自定义 `CallBodyPolicy` 时会同时存在两个 `CallBodyPolicy` 类型的 Bean（用户的 + `JdbcCallBodyPolicy`），而 `AiLiteAutoConfiguration.java:282` 用的是：

```java
CallBodyPolicy bodyPolicy = beanFactory.getBeanProvider(CallBodyPolicy.class).getIfAvailable();
```

多个候选时 `getIfAvailable()` 抛 `NoUniqueBeanDefinitionException`，**应用启动失败**。用缺陷换了个更大的缺陷。正确做法见 §2.3。

### F-38 解析路径绕过白名单与就绪检查 —— 属实，但要不要改取决于这两条路径的定位

**源码位置**：`LlmGateway.java:445-457`（`resolveFor` 公开且不调 `allows`）、`:1814`（`resolve` 走 `resolveExplicit`）；`ModelResolver.java:148-172`；调用方 `AdminController.java:384`、`SessionCompactor.java:422`、`AgentSessionLoop.java:544`。

`invoke` 和 `invokeAsync` 都在解析前做了 `resolver.allows(bizId)`（`LlmGateway.java:697`、`:1622`），`resolveFor` 没有。目前两个内部调用方传的都是已经过白名单的真实调用，所以实际没被利用；但这是个公开方法，外部可以直接调。

`resolveExplicit(..., true)` 被管理页「测试调用」用来发真实请求，绕过了就绪检查、出口保护和调用记录。`docs/desc-配置和运行时配置.md` 已经承认这一点。

**为什么不算好解决**：`resolveFor` 补一行 `allows` 很简单，但会改变一个公开方法的契约；管理页测试调用要么改成走网关（那就有了调用记录、也会占并发许可，得重新定义「测试」的含义），要么明确标注「不产生记录」。这属于设计决定，不是修 bug。

## 2. 修复方案

### 2.1 F-31：给缓存加版本号，读库期间的写入作废这次写回

思路：不清锁、不加锁到读库路径上（`level()` 在每次模型调用都会被调，让它在库查询期间持锁会把并发调用串起来）。改用「读之前记下版本，写回之前核对版本」。

`JdbcRuntimeCatalog` 的改法：

```java
// 每次改写或清缓存都 +1。读库线程靠它判断「我这份快照是不是已经过期」。
private final AtomicLong generation = new AtomicLong();

public void invalidate() {
    generation.incrementAndGet();
    snapshot = null;
    expiresAt = 0L;
}

private Snapshot load() {
    long now = System.currentTimeMillis();
    Snapshot current = snapshot;
    if (cacheMillis > 0L && current != null && now < expiresAt) {
        return current;
    }
    synchronized (this) {
        if (cacheMillis > 0L && snapshot != null && System.currentTimeMillis() < expiresAt) {
            return snapshot;
        }
        // 读库可能耗时，期间管理页可能写入并清了缓存。那样这份快照就是旧值，
        // 写回缓存会让旧配置再存活一个完整 TTL。重读，最多试三次。
        for (int i = 0; i < 3; i++) {
            long before = generation.get();
            Snapshot loaded = read();
            if (generation.get() == before) {
                snapshot = loaded;
                expiresAt = cacheMillis <= 0L ? 0L : System.currentTimeMillis() + cacheMillis;
                return loaded;
            }
        }
        // 连续被写入打断：退回不缓存。配置正在被频繁改，缓存本来也没意义。
        return read();
    }
}
```

`JdbcCallBodyPolicy` 用同一套：

```java
private final AtomicLong generation = new AtomicLong();

public String level() {
    String cached = cachedLevel;
    if (cached != null && System.currentTimeMillis() < expiresAt) {
        return cached;
    }
    long before = generation.get();
    String value = readLevel();
    // 查库期间有人 save/invalidate 过：不要用旧值覆盖刚写进来的新值。
    if (cacheMillis > 0L && generation.get() == before) {
        cachedLevel = value;
        expiresAt = System.currentTimeMillis() + cacheMillis;
    }
    return value;
}

public void save(String level) {
    ...原有校验与写库...
    generation.incrementAndGet();   // 先作废在途读，再写缓存
    if (cacheMillis > 0L) {
        cachedLevel = value;
        expiresAt = System.currentTimeMillis() + cacheMillis;
    }
}

public void invalidate() {
    generation.incrementAndGet();
    cachedLevel = null;
    expiresAt = 0L;
}
```

**已知残留**：极端交错下，某个已经在读库的调用方仍可能拿回写之前的档位，并据此多记（或少记）一次正文。这个窗口是「一次 SELECT 的时长」，任何缓存方案都无法消除；但**缓存本身不会停留旧值**，这是本条的验收点。

### 2.2 F-36：异常消息只留定位信息

`JdbcRuntimeCatalog` 三个 `readXxxMap`：

```java
} catch (Exception ex) {
    // 不带 ex.getMessage()：Jackson 的解析错误会带出出错位置的源文本，
```

### 2.3 F-37：管理页读真实策略，写不了就明确说为什么

不改注解（原因见 §1「F-37」）。改成让控制器同时拿到「可写」和「只读」两个来源：

`AiLiteAdminAutoConfiguration`：

```java

// 用户自定义了只读 CallBodyPolicy 时，管理页仍然要显示网关的真实档位，
// 否则页面说「不记录」、实际在记录，比不给页面更难排查。
CallBodyPolicy readOnly = policy == null ? readOnlyPolicy.getIfAvailable() : null;
```

`AdminController` 加一个接受 `CallBodyPolicy` 的重载（旧构造器保留并转调，保持二进制兼容）：

```java
@GetMapping("/ai-lite/admin/api/calls/body-level")
public Map<String, Object> bodyLevel() {
    Map<String, Object> data = new LinkedHashMap<String, Object>();
    data.put("level", currentLevel());
    data.put("options", bodyLevelOptions());
    // 只读时告诉页面：档位来自自定义实现，这里改不了。
    data.put("writable", Boolean.valueOf(bodyPolicy != null));
    return data;
}

@PutMapping("/ai-lite/admin/api/calls/body-level")
public Map<String, Object> saveBodyLevel(@RequestBody(required = false) Map<String, Object> body) {
    if (bodyPolicy == null) {
        throw new IllegalStateException(getReadOnlyPolicy() != null
                ? "档位由自定义 CallBodyPolicy 提供，管理页只能读。要改档位请在实现里处理"
                : "调用记录档位不可用");
    }
    ...
}

private String currentLevel() {
    if (bodyPolicy != null) {
        return bodyPolicy.level();
    }
    CallBodyPolicy readOnly = getReadOnlyPolicy();
    return readOnly == null ? CallBodyPolicy.NONE : readOnly.level();
}
```

代价：管理页前端要能接受多出来的 `writable: false`（不处理也不会坏，只是保存时才看到错误消息）。前端改动留给管理页那轮，本批只保证接口返回真实档位。

### 2.4 F-32：给目录加可选事务

照 `JdbcPromptStore` 的写法，构造函数多一个可空的事务管理器，老的五个参数构造器保持不变。

`JdbcRuntimeCatalog`：

```java
private final TransactionTemplate writes;     // 写侧：DELETE + INSERT 必须同进同退
private final TransactionTemplate reads;      // 读侧：三条查询要看到同一个时刻

public JdbcRuntimeCatalog(JdbcTemplate jdbc, String providerTable, String modelTable,
                          String bizTable, int cacheSeconds) {
    this(jdbc, providerTable, modelTable, bizTable, cacheSeconds, null);
}

/** @param txManager 事务管理器；null 表示没有，退化为原来的逐条提交 */
public JdbcRuntimeCatalog(..., PlatformTransactionManager txManager) {
    ...
    if (txManager == null) {
        this.writes = null;
        this.reads = null;
    } else {
        this.writes = new TransactionTemplate(txManager);
        this.reads = new TransactionTemplate(txManager);
        this.reads.setReadOnly(true);
    }
}
```

`saveOverlay`：

```java
public void saveOverlay(final ProviderOverlay overlay) {
    ...原有校验...
    inWriteTransaction(new Runnable() {
        public void run() {
            jdbc.update("DELETE FROM " + providerTable + " WHERE PROVIDER_ID = ?", overlay.getProviderId());
            jdbc.update("INSERT INTO " + providerTable + " (...) VALUES (...)", ...);
        }
    });
    invalidate();
}
```

`saveBinding` 与 `JdbcCallBodyPolicy.save` 同样处理。`read()` 整段包进 `reads`。

装配侧：`AiLiteCatalogAutoConfiguration` 用 `ObjectProvider<PlatformTransactionManager>` 取。**这里用 `getIfUnique()` 而不是 `getIfAvailable()`**——容器里有多个事务管理器时 `getIfAvailable()` 会抛 `NoUniqueBeanDefinitionException`，让应用起不来；而这里应该降级为「不包事务」并打一条 WARN。

```java
PlatformTransactionManager txManager = transactions.getIfUnique();
if (txManager == null && transactions.stream().count() > 1) {
    log.warn("容器里有多个事务管理器，无法确定用哪个，目录读写退回逐条提交。"
            + "请给本应用的事务管理器加 @Primary，否则 DELETE 成功、INSERT 失败时配置会丢");
}
```

> **与既有写法的差异**：`AiLitePromptJdbcAutoConfiguration.java:61` 用的是 `transactionManager.getIfAvailable()`，多数据源场景下有同样的启动失败风险。本批只改目录这一侧，提示词存储那处记在 §5 作为后续项，避免一次动两处扩大回归面。

**为什么这条排在 F-33 前面**：唯一索引的升级脚本要「先清重复行、再建索引」，这两步必须在一个事务里，否则中途失败会留下半清状态。

### 2.5 F-34：把「没填」和「填了 0」分开

分两半，各解决一半症状。

**前半：`setReady(true)` 拒绝参数不全的行**。这是「已启用但参数全空」这个状态的入口，在这里拦一次，后面所有路径都不用再猜。

```java
public void setReady(String providerId, String modelId, boolean ready) {
    ...原有校验...
    if (ready) {
        CatalogModel row = findModel(providerId, modelId);
        List<String> missing = new ArrayList<String>();
        if (row == null) {
            throw new IllegalStateException("模型不存在: " + modelId);
        }
        if (row.getContextWindow() == null) missing.add("CONTEXT_WINDOW");
        if (row.getMaxTokens() == null) missing.add("MAX_TOKENS");
        if (row.getInputModes().isEmpty()) missing.add("INPUT_MODES");
        if (row.getReasoningFlag() == null) missing.add("REASONING");
        if (Strings.isBlank(row.getThinkingFormat())) missing.add("THINKING_FORMAT");
        if (!missing.isEmpty()) {
            // 静默放行会让上下文预算和图片检测整条失效，且页面上看不出来。
            throw new IllegalStateException("模型参数不完整，不能启用。缺: " + missing);
        }
    }
    ...
}
```

**后半：`CatalogModel` 能表达「没填」**。目前只有 `REASONING` 卡在类型上（原始 `boolean`），其余四项用的是 `Integer`/`String`/`List`，本来就带 null。

加一个可空访问器 + 一个目录行专用工厂方法，**既有构造器签名一个都不动**（`ai-lite-llm` 走 japicmp 比对，删改签名会让契约检查失败）：

```java
/** @return 是否支持推理；null 表示数据库没填，解析时应沿用配置文件 */
public Boolean getReasoningFlag() {
    return reasoningFlag;
}

/**
 * 目录行专用：{@code reasoningFlag} 为 null 表示这一列是 NULL。
 * 老的 boolean 构造器语义不变（false 就是「不支持」，不是「没填」）。
 */
public static CatalogModel fromCatalogRow(String providerId, String modelId, boolean ready,
        Boolean reasoningFlag, List<String> inputModes, ...) { ... }
```

`JdbcRuntimeCatalog.toModel` 改用它，`REASONING` 列用「读出来是不是 null」判断。`ModelResolver.toConfigModel` 改成：

```java
model.setReasoning(row.getReasoningFlag() != null ? row.getReasoningFlag().booleanValue()
        : (yaml != null && yaml.isReasoning()));
model.setContextWindow(row.getContextWindow() != null ? row.getContextWindow()
        : (yaml == null ? null : yaml.getContextWindow()));
model.setMaxTokens(row.getMaxTokens() != null ? row.getMaxTokens()
        : (yaml == null ? Integer.valueOf(8192) : yaml.getMaxTokens()));
model.setInput(row.getInputModes().isEmpty()
        ? (yaml == null || yaml.getInput().isEmpty()
            ? Collections.singletonList("text") : new ArrayList<String>(yaml.getInput()))
        : new ArrayList<String>(row.getInputModes()));
model.setThinkingFormat(Strings.isBlank(row.getThinkingFormat())
        ? (yaml == null || Strings.isBlank(yaml.getThinkingFormat())
            ? "reasoning-effort" : yaml.getThinkingFormat())
        : row.getThinkingFormat().trim());
```

改完后的规则一句话：**启用（READY=1）的模型必须有完整参数；没启用的行按数据库 → 配置文件 → 内置默认 的顺序回落**。这条要写进 `docs/desc-配置和运行时配置.md` 和 `docs/ref-配置.md`。

**兼容性提示**：这条会让「先 setReady 再填参数」的旧操作顺序报错。管理页现在的流程是先保存参数、再启用，符合新规则；但库里已有的「已启用但参数不全」的行会在下次启动后第一次被调用时报错。这需要在 CHANGELOG 里写明，并提供一条自查 SQL：

```sql
SELECT PROVIDER_ID, MODEL_ID FROM AI_LITE_MODEL
WHERE READY = 1 AND (CONTEXT_WINDOW IS NULL OR MAX_TOKENS IS NULL
  OR INPUT_MODES IS NULL OR REASONING IS NULL OR THINKING_FORMAT IS NULL);
```

### 2.6 F-33：用锁保证「先查再插」原子，不动表结构

**方案变更（实施时定）**：原计划加 `(PROVIDER_ID, MODEL_ID)` 唯一索引。实施时改为
应用层加锁，原因是不需要改表结构、升级时不用人工清理存量重复行。锁的实现按部署形态
分两种，由配置项显式声明：

| 部署形态                                   | 实现                  | 生效范围 |
| -------------------------------------- | ------------------- | ---- |
| 单节点（默认）                                | `LocalModelKeyLock` | 本进程  |
| 多节点（`ai-lite.catalog.multi-node=true`） | `RedisModelKeyLock` | 跨进程  |

**为什么必须显式配置**：部署形态代码猜不出来——同机多进程、容器多副本都算多节点，
但看上去都是「一个应用」。配错的代价是重复写入悄悄发生，所以配成多节点却拿不到
`StringRedisTemplate` 时**启动失败**，不退回进程内锁。

**锁的写法**：

```java
public boolean insertModelIfAbsent(String providerId, final String modelId) {
    if (findModel(providerId, modelId) != null) {
        return false;   // 缓存命中，省一次拿锁
    }
    // 「先查再插」必须原子，否则两个请求都查不到、都插入。
    return modelKeyLock.withLock(providerId, modelId, new Callable<Boolean>() {
        @Override
        public Boolean call() {
            return insertModelIfAbsentInLock(providerId, modelId);
        }
    }).booleanValue();
}
```

锁内要**重新查一次**：等锁期间别的请求可能已经插进去了。

`RedisModelKeyLock` 的三个要点：

1. `SET NX PX` 抢锁，带租期。进程崩溃时锁不能永久残留。
2. 释放用 Lua 比对 token 再删。否则会出现「本进程的锁已过期被别人拿到，本进程收尾时
   把别人的锁删了」。
3. 抢锁失败带重试和总超时，超时报错并指出是哪个模型，不无限等待。

**仍然要保留的部分**：读取顺序确定化（`ORDER BY ... UPDATE_TIME DESC, MODEL_ROW_ID DESC`

+ 按排序取第一条）。锁只能拦住走 `insertModelIfAbsent` 的写入，直连 SQL 或升级前的
  历史数据仍可能有重复行，读路径必须给出确定答案。

## 5. 本计划不做的部分

**F-35 管理接口鉴权**：需要先定 token 来源、未配置时的行为、只读角色、与反向代理认证的关系。在没有这些答案前加一个「配置项里写死 token」的校验，会给人一种「已经安全了」的错觉，而配在 YAML 里的 token 会进代码仓库。建议单独写一篇计划，至少要覆盖：token 从环境变量读、缺失时启动失败（而不是默认放行）、接口返回统一的 401 文案。

**F-38 解析路径**：`resolveFor` 补 `allows` 是一行代码，但它是公开方法，改变契约要走 `docs/plan/012-对外契约冻结.md` 的流程。管理页「测试调用」是否应该产生调用记录、是否应该占并发许可，是产品决定。本轮只更新 `docs/desc-配置和运行时配置.md` 里对这两条路径的说明，把「不产生调用记录」写得更显眼。

**`AiLitePromptJdbcAutoConfiguration.java:61` 的 `getIfAvailable()`**：与本计划 §2.4 是同一个隐患（多事务管理器时启动失败），但它在提示词存储模块，不在 3.3 的 8 条里。改动会和 §2.4 争同一轮回归窗口，等本批落地后单独一行修掉。
