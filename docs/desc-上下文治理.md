# 上下文治理：预算、投影与压缩

> 适用版本：0.1.8
> 相关代码：`AgentSessionLoop`、`internal/session/ContextBudget`、`internal/session/SessionCompactor`、`util/TokenEstimator`、`CompactionEntry`、`AgentSessionEntry`
> **本文在哪一层**：会话层（`AgentSessionLoop` 发请求前的准备阶段）。
> **讲什么**：会话历史怎么变成"这一轮真正发给模型的消息"（投影）、怎么判断会不会撑爆窗口（预算）、撑爆了怎么自救（压缩），以及为什么这么设计。
> **不讲什么**：单次调用与工具循环的行为 → [单次模型调用入口](desc-单次调用.md)、[AgentLoop 发给 LLM 的上下文](desc-AgentLoop上下文.md)；配置字段速查 → [配置参考](ref-配置.md) §5.1；怎么调 API → [上层调用 API](guide-上层调用API.md) §5。生词查 [术语表](ref-术语表.md)。

## 0. 一句话结论

会话里存的是**全量条目，一条都不删**；每轮发请求前**现场算出**该发给模型的那一段；只有当前算出来会超窗口时才**花一次 LLM 调用**生成摘要，并把摘要作为一条新条目追加进去。

三个动作互相独立：

| 动作 | 花不花钱 | 落不落盘 | 何时发生 |
| --- | --- | --- | --- |
| 投影（projection） | 不花 | 不落盘 | 每次发请求前 |
| 预算检测（budget） | 不花 | 不落盘 | 每次发请求前 |
| 压缩（compaction） | **花一次摘要调用** | **落盘**（追加 `CompactionEntry`） | 估算超线时 |

把这三件事分开，是为了同时满足两个看起来矛盾的要求：**默认开启压缩**（用户决策 Q3），**又能随时恢复到完整历史**。

---

## 1. 为什么不能"原地替换"

最直接的做法是超限时把老消息删掉、换成一段摘要。这个做法有一个致命问题：**它是不可逆的**。

- 摘要质量差 → 模型开始答非所问 → 想临时关掉压缩看看 → 但原文已经没了
- 压缩逻辑有 bug → 丢掉的消息无法找回
- 想换一个 `keep-recent-tokens` 重新压 → 没有原始数据，压不了

所以本项目采用**保留原始 + 构建时投影**：

```text
数据库里存的（唯一事实源，从不改写）
┌──────────────────────────────────────────────────┐
│ [system:你是助手][system:输出JSON][user1][asst1] │
│ [user2][asst2][compaction:{summary,firstKept}]   │
│ [user3][asst3]                                    │
└──────────────────────────────────────────────────┘
                    │
                    │  ← 每次发请求前现场投影（不落盘）
                    ▼
本次发给模型的
┌──────────────────────────────────────────────────┐
│ [system:你是助手]                                 │  ← 前缀区，永不压缩
│ [system:输出JSON]                                 │
│ [system:摘要]                                     │  ← compaction.summary
│ [user2][asst2][user3][asst3]                     │  ← firstKept 之后
└──────────────────────────────────────────────────┘
```

投影是**纯函数**：同样的条目数组 + 同样的配置，永远算出同样的结果。它不缓存结果，因为配置随时可能改（改了 `keep-recent-tokens` 下一轮立刻按新规则算，不需要迁移数据）。

## 2. 投影规则

### 2.1 三条规则

```
1. 前缀区 = 数组开头「连续」的 SYSTEM 条目，原样保留在最前
2. 从数组末尾往前找【最后一条】CompactionEntry
     ├─ 没有 → 剩余部分 = 前缀区之后的全部 message 条目
     └─ 找到 c → 剩余部分 = [system(c.summary)] + 从 c.firstKeptEntryId 往后的 message
3. 结果 = 前缀区 + 剩余部分
```

代码位置：`AgentSessionLoop.projectEntries`。

### 2.2 前缀区（会话级系统提示）

这是本项目对"会话级 system prompt"的解法，不加新字段、不改数据模型。

**规则**：从条目 0 开始**连续**的 SYSTEM 条目构成前缀区；遇到第一条非 SYSTEM 立刻结束。

```text
[m1: system "你是简历筛选助手"]     ┐
[m2: system "输出必须是 JSON"]      ┘ 前缀区：永远保留，不进摘要
[m3: user "帮我看看这份简历"]        ┐
[m4: assistant "..."]                │ 可压缩区
...                                  ┘
```

为什么不用 pi 的 `systemMessage` checkpoint 字段：checkpoint 会在每次压缩时快照一份完整系统提示，于是存在"快照与真实值不一致"的失效点。前缀区方案不存快照——系统提示就在条目数组开头，投影时直接取，天然是最新的，也少一份冗余存储。

**边界**：

| 情形 | 行为 |
| --- | --- |
| 前缀区之后又追加了 SYSTEM | 属于可压缩区，会随压缩消失（投影时被 `LlmTexts.fold` 合并到最前，但内容不在了） |
| SYSTEM、USER、SYSTEM 交错 | 只有第 1 条算前缀区；第 3 条按普通消息处理 |
| 前缀区过长 | 一直占上下文，不计入可压缩预算——这是有意的，系统提示本来就该常驻 |

### 2.3 多次压缩：只认最后一条

条目数组里可能有 0 条、1 条或 N 条 `CompactionEntry`（会话很长时会多次压缩）。**投影只认最后一条**，更早的压缩条目对投影无影响。

它们仍然保留，用于：

- 审计（"这个会话被压过几次、每次压掉了多少"）
- 重复压缩的起点（见 §3.3）

### 2.4 两个人人都会问的问题

**投影会重复花钱吗？** 不会。投影是纯内存遍历 + 拼装，不调用任何模型。

**摘要什么时候生成？** 只在"当前投影估算 > 触发线"时生成一次，然后永久复用。时间线示例（32768 窗口，触发线 24576）：

```text
第 1 次续聊   估算 20000  → 未超线 → 投影 → 发请求        💰 1 次模型调用
第 2 次续聊   估算 24000  → 未超线 → 投影 → 发请求        💰 1 次
第 3 次续聊   估算 26000  → 超线了！
                            ├─ 调 LLM 生成摘要            💰 +1 次（摘要）
                            ├─ 落盘 CompactionEntry
                            └─ 投影后 14000 → 发请求      💰 1 次
第 4 次续聊   估算 15000  → 未超线 → 投影 → 发请求        💰 1 次
第 5 次续聊   估算 18000  → 未超线 → 投影 → 发请求        💰 1 次
...
第 N 次续聊   估算 25000  → 超线了！再压一次              💰 +1 次（摘要）
```

第 3 次生成的摘要在第 4、5、…、N-1 次续聊中被反复使用，**没有重新调用 LLM**。这就是 §4 那条不变式为什么重要——余量越大，需要重新压缩的频率越低。

## 3. 预算检测与压缩

### 3.1 估算对象必须包含本轮新消息

**这是最容易实现错的地方。** `prepare()` 已经把本轮新消息拼进待发送列表，压缩发生在它之后，所以：

```text
估算与投影的对象 = 前缀区 + [已投影的历史] + 本轮新消息

不是：
  只估历史        ← 会漏掉本轮新消息，可能压完还是超
  只估新消息      ← 完全没意义
```

实施时踩过一个相关坑：给投影追加本轮消息时误用了**完整历史列表**，把已被压缩条目挡掉的消息又加回去，等于压缩失效。正确做法只追加"本轮新增且尚不在会话中的 id"。

### 3.2 估算算法

按字符类型加权（`TokenEstimator`）：

| 字符类别 | 权重（token/字符） | 依据 |
| --- | --- | --- |
| ASCII / 拉丁 | 0.25 | 英文约 4 字符/token |
| 中日韩文字 | 0.6 | 常用汉字接近 1 字/token，取偏保守值 |
| 其他（标点、emoji 等） | 0.5 | 折中 |

每条消息另加 4 token 固定开销（角色标记、分隔符）。

**为什么不引 tokenizer**：JDK 8 生态没有可靠的通用 BPE 实现，引入会让依赖面变宽，而且各供应商分词表不同，用 OpenAI 的 BPE 估国产模型反而更不准。目标是"够用来判断该不该压缩"，不是精确计费——精确值以供应商返回的 usage 为准。

**为什么不能简单用 `字符数 / 2.5`**：该公式对英文大致成立，但中文字符通常占 1 token 左右，除以 2.5 会低估 40%~60%。这是一个中文为主的库，低估的后果是"以为没超，其实超了"，供应商直接报错。测试里有硬断言防止有人改回普通除法。

### 3.3 压缩切点的三条硬规则

```
1. 从最后一条前缀 SYSTEM 之后开始，向前累计到 keepRecentTokens 即停
2. 切点必须落在 USER 消息上
3. 绝不拆开 toolCall 与 toolResult
```

规则 2 和 3 是同一个原因：投影后发给模型的历史以「切点那条消息」开头。如果切点是 assistant 或 tool_result，模型看到的第一条就是"半截对话"，多数供应商会直接返回 400。

**切点不能越过已落盘历史**。这是一个实施中发现的真实缺陷：切点原本可能落在本轮尚未写入会话的新消息上，于是 `firstKeptEntryId` 指向一个不存在的 id，投影时找不到就退化成"压缩条目之后"，实际等于没压。现在切点上限被限制在已落盘的那一段。

### 3.4 重复压缩的起点

```
首次压缩：摘要输入 = [前缀区之后 .. 新切点)
重复压缩：摘要输入 = 上一条 compaction.summary（作为迭代上下文）
                   + [上次 firstKeptEntryId .. 新切点)
```

**必须这样**。否则每次都从数组开头摘要，输入量随会话增长，最终退化成"摘要请求自己超窗口"——要压缩的正是刚超限的那段历史。

两种情况的摘要输入都**不含前缀区**，避免每轮重复摘要同一段系统提示。

### 3.5 分块摘要

```
摘要输入预算 = 摘要模型窗口 - summaryMaxTokens - 安全余量(256)
     ├─ 待摘要内容 <= 预算 → 一次调用
     └─ 超过 → 按消息边界分块，逐块摘要并把上一块摘要作为下一块上下文
```

分块也按消息边界切，不切断单条消息。

### 3.6 决策表

超限之后到底做什么，全部收敛在这张表里（`AgentSessionLoop.enforceBudget`）：

```
窗口未知（contextWindow <= reserve）        → 跳过全部检查
估算 <= 触发线                              → 不压缩，发请求
估算 > 触发线 且 compaction.enabled=false   → 抛 CONTEXT_OVERFLOW
估算 > 触发线 且 可压缩                     → 压
    ├─ 成功且回到线内 → 发请求
    ├─ 成功但未下降   → 抛 CONTEXT_OVERFLOW（防死循环）
    └─ 失败           → 抛 CONTEXT_OVERFLOW（不降级成截断）
```

**超限就报错，不静默丢历史。** 静默修改对话历史比报错更难排查：用户看到的是"模型忘了前面说过的话"，日志里什么都没有。

### 3.7 阈值不变式（启动期校验）

```
不变式 1：keepRecentTokens + summaryMaxTokens < contextWindow - reserveTokens
不变式 2：contextWindow <= reserveTokens → 视为「窗口未知」，禁用预算检查
不变式 3：maxPerRun >= 1
不变式 4：压缩后估算 < 触发线
```

默认值（32768 窗口）：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `reserve-tokens` | 8192 | 留 1/4 给模型回复 |
| `keep-recent-tokens` | 12000 | 必须 < 32768-8192=24576 |
| `summary-max-tokens` | 2048 | |
| 触发线 | 24576 | |
| 压缩后目标 | ≈14048 | < 触发线，不变式 1 满足 |

**为什么要在启动期校验**：初版曾用 `reserve=16384` + `keep=20000`，在 32768 窗口下触发线 16384 < 保留 20000，**必然每轮重压**；窗口 ≤16384 时每次请求都抛异常。这类错误在运行期只表现为"账单异常高"，不报错，极难定位。不满足不变式 1 时启动直接失败，错误消息给出三个实际数值。

### 3.8 压缩关闭时投影怎么办

`applyCompaction` 与 `budget.compactionEnabled()` 是**两个独立开关**：

| `ai-lite.context.enabled` | `compaction.enabled` | 行为 |
| --- | --- | --- |
| false | 任意 | 不做预算检查；投影**仍应用**已有压缩条目 |
| true | false | 做预算检查，超限抛错；投影**忽略**压缩条目，回到完整历史 |
| true | true | 全功能 |

分开的理由：前者是"我不想要预算判断"，后者是"我不想要压缩改我的历史"。混用一个开关会导致"关掉预算判断时历史突然变长"这种意外。

## 4. 条目化数据模型

### 4.1 四种类型

| 类型 | 类 | 进上下文 | 说明 |
| --- | --- | --- | --- |
| `message` | `AgentSessionMessage` | 是 | 对话消息 |
| `compaction` | `CompactionEntry` | 只把 `summary` 作为一条 SYSTEM 注入 | 压缩摘要 + 保留区起点 |
| `session_info` | `SessionInfoEntry` | 否 | 会话元信息（标题等） |
| `usage` | `UsageEntry` | 否 | 单轮用量 |

为什么条目化而不是给 `AgentSession` 加字段：压缩可以在一个会话里发生多次，字段只能表达"最后一次"；条目能保留全部历史，为将来的 append-only 存储铺路。

### 4.2 两套视图

```java
AgentSession
  ├─ getEntries()  → List<AgentSessionEntry>    全量（含 compaction）
  └─ getMessages() → List<AgentSessionMessage>  过滤视图（只返 message）
```

`getMessages()` 的**签名不变**（二进制兼容），内部改为过滤。这样既保住契约，也不用改动几十处既有调用点。

`getMessages()` 返回**只读副本**：修改它不影响会话。写消息必须用 `setMessages(...)`，它内部走按 id 对齐的 `mergeMessages`。

### 4.3 为什么合并要按 id 而不是按位置

`mergeMessages` 按消息 **id** 对齐，非消息条目保持原位。三个动作对应三种语义：

| 情况 | 语义 |
| --- | --- |
| id 在新列表里 | 原位替换（内容可能变了） |
| id 不在新列表里 | 视为删除，从自己的槽位移除 |
| 新 id 不在旧列表里 | 追加到末尾 |

**按位置对齐会坏掉**：删除中间一条消息时，后续消息会全部左移一格，于是它们"跨过"了压缩条目，跑到摘要前面去了。语义上这等于"本应被压缩掉的消息又出现在摘要之后"。这个问题是 RT6 测试抓出来的。

### 4.4 三类入口的丢条目风险

历史上这里有三处"只写 message"的缺陷，任一处生效都足以让压缩**每轮算、每轮花钱、每轮被丢掉**，而且不报错：

| 入口 | 症状 |
| --- | --- |
| `AgentSessionStoreSupport` 三个消息级方法 | 调一次 `appendMessage` 就丢 |
| `AgentSessionCodec.encodeSession` | Redis 缓存命中一次再写回就丢 |
| `AgentSessionLoop.finish` | **每轮续聊都丢**（它曾用 `new AgentSession()` 重建对象） |

`finish` 那条最致命，因为它是每轮的必要路径。现在的写法是 `AgentSession.copyOf(session)` + `mergeMessages`，绝不重建对象。

这套约束由 `SessionEntryRoundTripGateTest`（RT1–RT7）锁住，任何一条失败都意味着修复不完整。

## 5. 并发与多节点

多个实例同时判定超限时，各压一次 = 双份钱，后写者还会撞版本冲突。处理方式：

```text
实例 A / B 同时判定超限
    ├─ A 抢到租约 → 生成摘要 → 落盘
    └─ B 抢不到   → 跳过压缩，直接用现有投影发请求（不报错）
```

租约是**尽力而为**，不是正确性依赖：方案是"追加条目"，两个都压也只是多一条摘要，数据不会损坏。因此抢不到的一方静默跳过是正确的——等 A 压完，B 下一轮读到的估算自然变小。

租约必须可过期抢占，否则节点崩溃会让压缩永久卡死。

## 6. 已知边界

| 边界 | 说明 |
| --- | --- |
| 只估文本 | 图片 base64 与工具 schema 不计入估算 |
| 估算非精确 | 与真实 tokenizer 有偏差，靠 `reserve-tokens` 留余量兜住 |
| 摘要质量决定效果 | 保留最近 `keepRecentTokens` 是主要保险；不行就调大它 |
| `afterTool` 改写不再截断 | 截断发生在钩子之前，钩子是调用方的明确意图，框架不二次裁剪 |
| 压缩后落盘失败要报错 | 否则下次续聊会重新压缩、重新花钱，且用户看不到异常 |

最后一条的实现约束：`finish` 里 `store.save(toSave)` 外面**没有** try-catch，异常会自然冒泡。实施时不要给它加"容错"包装。
